# 설계: 제로카피 경로를 라이브러리, 프로그램, 패키지로 배포하기

**상태:** 논의를 위한 제안이다. 여기 있는 것은 아직 만들지도, 정하지도, 재지도 않았다. 이름(`rkzc`, `rkzc-detect`)은 임시다.

**목표:** NanoPi R6C를 가진 사람이 패키지 하나를 설치하면 변형 C의 경로를 쓸 수 있게 한다. 하드웨어 디코드(MPP), RGA에서의 변환과 레터박스, NPU 추론으로 이어지고 픽셀을 CPU로 복사하지 않는 경로다. 바로 도는 프로그램으로도, 그 위에 만들 수 있는 라이브러리로도 제공한다.

**이 경로의 값어치:** M1의 H1 지점(8채널, 채널당 초당 5회 추론)에서 프로세스 CPU가 120초당 B는 43.3초, C는 18.6초였다([M1](../report/M1.ko.md)). M3가 초기화한 보드에서 두 숫자를 다시 얻었다([M3](../report/M3.ko.md)). 패키지는 이 경로를 담고, 벤치마크는 담지 않는다.

## 제안 요약

세 층이고, 코드는 한 벌이다.

| 층 | 무엇인가 | 누가 쓰나 |
|---|---|---|
| `librkzc` | C++ 라이브러리: 스트림과 모델을 주면 콜백으로 검출 결과를 준다 | 자기 프로그램을 짜는 사람 |
| `rkzc-detect` | 라이브러리 위의 얇은 프로그램: 설정 파일을 읽고 JSON 줄을 내며 systemd가 돌린다 | 그냥 돌리고 싶은 사람 |
| `rkzc_*.deb` | 위 둘과 헤더, 서비스 파일, 예시 설정 | 모두. `apt install ./rkzc_*.deb`로 설치한다 |

- **라이브러리만 내지 않는 이유:** 써 보려면 빌드 환경부터 갖춰야 한다.
- **프로그램만 내지 않는 이유:** 출력이나 후처리를 바꾸려면 소스를 고쳐야 한다.
- **프로그램을 라이브러리 위에 얹는 이유:** 유지하고 시험할 경로가 둘이 아니라 하나가 된다.

## 라이브러리

### 제공하는 것

크기를 보이기 위한 인터페이스 스케치다. 확정이 아니다.

```cpp
namespace rkzc {

struct Detection { float x, y, w, h, score; int cls; };   // 원본 프레임의 픽셀 좌표

struct Frame {
    int channel;
    int64_t pts;                 // 스트림의 타임스탬프
    int64_t capture_ns;          // 프레임이 디코더에서 나온 시각(CLOCK_MONOTONIC)
    const Detection* detections;
    int count;
};

struct Config {
    std::vector<std::string> sources;   // 채널마다 RTSP 주소나 파일 하나
    std::string model;                  // .rknn 파일
    int every_nth_frame = 6;            // 6: 30 fps 스트림에서 초당 5회 추론
    float conf = 0.25f, nms_iou = 0.45f;
};

class Detector {
public:
    static Result<std::unique_ptr<Detector>> open(const Config&);   // 중단이 아니라 오류를 돌려준다
    void on_frame(std::function<void(const Frame&)>);               // 작업 스레드에서 호출된다
    void on_event(std::function<void(const Event&)>);               // 스트림 끊김, 재연결, 프레임 드롭
    void start();
    void stop();
    Stats stats() const;                                            // 채널별: 디코드, 추론, 드롭 수
};

}  // namespace rkzc
```

- **숨기는 것:** DRM PRIME 프레임, dma-buf 파일 디스크립터, 입력 슬롯, RKNN 컨텍스트 세 개와 그 바인딩. 사용자는 기본적으로 픽셀 버퍼를 보지 않는다.
- **처음에는 고정하는 것:** H.264 입력, 모든 채널에 모델 하나, NPU 컨텍스트 세 개(코어당 하나), 이 저장소가 이미 다루는 YOLOv8n과 YOLOv10n의 출력 형식.

### 코드에서 바꿔야 하는 것

경로는 `src/core`와 `src/preprocess`에 있지만, 다른 프로그램에 넣기 위해서가 아니라 재기 위해 쓴 코드다. 코드를 읽고 찾은 차이는 이렇다.

| 지금 | 필요한 것 |
|---|---|
| 실패하면 프로세스가 중단된다(`VideoSource::open`, `NpuContexts::open`의 "dies on failure") | 호출한 쪽에 오류를 돌려준다 |
| 타임라인이 고정이다: 워밍업, 120초 창, 종료(`PipelineConfig`) | 멈추라고 할 때까지 돈다 |
| 스트림이 끝나거나 실패하면 그 채널은 그대로 멈춘다 | 간격을 늘려 가며 재연결하고, 이벤트로 알린다 |
| 프레임마다 타임스탬프 일곱 개와 초당 샘플을 메모리에 둔다(`RunResult`) | 기본은 끔. 카운터만 둔다 |
| 레터박스가 16:9 원본과 640 × 640 입력을 가정한다("640x360 image band") | 스트림과 모델의 크기에서 계산한다 |
| 검출 결과를 세기만 하고 내주지 않는다(`FrameRecord::detections`) | 원본 프레임 좌표로 내준다 |
| `core`가 변형 A, B를 위해 OpenCV를 링크하는 정적 라이브러리 하나다 | OpenCV 없이 C의 경로만 |
| 내부 헤더가 FFmpeg과 RKNN의 헤더를 포함한다 | 둘 다 없는 공개 헤더 |

- **잰 것을 건드리지 않고 가는 방법:** 등록한 코드(`freeze-m1`부터 `freeze-m3`까지)는 그대로 두고, `bench_main`은 계속 거기서 빌드한다. 라이브러리는 공유할 수 있는 소스는 같이 쓰고, 위의 변경은 그 뒤에 둔다.
- **어긋남을 막는 장치:** 같은 파일을 `bench_main`의 변형 C와 `librkzc`에 넣고 검출 결과를 비교하는 테스트. `tools/m2_equivalence`가 이미 후처리 arm 사이에서 이런 비교를 한다.

## 프로그램

- **입력:** 설정 파일 하나, `/etc/rkzc/detect.toml`. 소스, 모델, 샘플링, 임계값, 출력이 갈 곳을 적는다.
- **출력:** 추론한 프레임마다 JSON 객체 하나를 stdout이나 유닉스 소켓으로 낸다. 한 줄에 채널, 타임스탬프, 검출 결과가 들어간다.
- **실행:** `systemctl enable --now rkzc-detect`. 로그는 저널로 가고, 스트림 이벤트는 로그 줄이 된다.
- **첫 버전에 넣지 않는 것:** MQTT, HTTP, 영상에 상자 그리기, 녹화. 모두 JSON 줄을 받아 쓰는 쪽이라 따로 작은 프로그램으로 만들 수 있다. 무엇이 중요한지는 용도에 달렸고, 용도는 아직 정해지지 않았다.

## 패키지와 의존성

설치에서 어려운 부분은 이 저장소의 코드가 아니다. 깨끗한 FriendlyElec 이미지에 무엇이 없는지는 M3의 설정 스크립트가 보여 준다([reproduce.md](../notes/reproduce.ko.md)).

| 의존성 | 이미지에 있나 | apt에 있나 | 선택지 |
|---|---|---|---|
| 커널 드라이버(rknpu, rga, MPP) | 있음 | — | 요구한다. 설치할 때 버전을 확인한다 |
| librga, MPP 사용자 공간 | 있음 | 없음(FriendlyElec 자체 패키지) | 이미지의 것에 의존한다. 버전을 확인한다 |
| librknnrt 2.3.2 | **없음** | 없음 | 설치할 때 SHA-256과 함께 받는다. 라이선스가 담는 것을 허용하지 않는다 |
| ffmpeg-rockchip | 없음 | 없음 | (가) 빌드한 라이브러리 네 개를 담는다, (나) 설치할 때 빌드한다(보드에서 6분) |
| 모델(`.rknn`) | 없음 | 없음 | 패키지에 넣지 않는다(AGPL 3.0). 별도 명령으로 이 저장소의 Release에서 받거나 사용자의 것을 쓴다 |

- **라이선스가 정한 것**([licences.ko.md](licences.ko.md)):
  - **ffmpeg-rockchip**은 여기서 빌드한 대로 LGPL v3이다. 라이브러리 네 개를 `/opt/rkzc/lib` 아래에 따로 담는다(설정 스크립트가 `/opt/ffmpeg-rockchip`에 두는 것처럼). 그러면 Ubuntu의 FFmpeg과 충돌하지 않는다. 패키지에는 라이선스 전문을, Release에는 정확한 소스를 둔다.
  - **librknnrt**는 설치할 때 Rockchip의 저장소에서 받는다. 라이선스가 재배포 권리를 주지 않고 RKNN 헤더는 복제를 금지하므로, 둘 다 패키지에도 이 저장소에도 넣지 않는다.
  - **모델**은 AGPL 3.0이며 패키지 밖에 둔다.
  - **이 저장소**는 Apache 2.0이다.
- **버전:** 패키지는 시험한 이미지(`rom-version` 20251222, 커널 6.1.141, rknpu 드라이버 0.9.8)를 밝히고, 모르는 커널 드라이버나 런타임에서는 분명한 메시지와 함께 거부한다. M3의 고정 인벤토리 키가 출발 목록이다.
- **만드는 방법:** 저장소의 스크립트로 보드나 arm64 컨테이너에서 만들고, Release 첨부 파일로 공개한다. 처음에는 apt 저장소를 두지 않는다.

## 패키지가 약속하는 것과 약속하지 않는 것

- **약속하는 것:** 패키지가 돌리는 경로가 변형 C의 것이고, 시험한 이미지에서 `bench_main`과 대조했다는 것.
- **약속하지 않는 것:** 다른 보드, 이미지, 카메라, 모델에서 M1의 숫자. M1부터 M3까지는 보드 하나에서, 파일로 만든 1080p RTSP 스트림으로 쟀다. 사용자가 아끼는 CPU는 해상도, 프레임률, 모델에 달렸다. 사용자 자신의 CPU와 지연을 보고하는 작은 명령을 패키지에 넣을 수 있다.
- **아직 전혀 재지 않은 것:** 라이브러리 자체의 부담(콜백, 좌표 변환, JSON). 패키지한 경로에 숫자를 내세우려면, 마일스톤처럼 먼저 계획이 있어야 한다.

## 열린 질문

설계를 바꾸는 질문이고, 답은 소유자가 정한다.

1. **보드의 범위:** FriendlyElec 이미지의 NanoPi R6C만인가, 다른 RK3588 보드와 이미지도인가? 뒤쪽이면 버전 확인이 몇 배로 늘어난다.
2. **모델:** YOLOv8n과 YOLOv10n만인가, 사용자가 후처리를 주는 임의의 `.rknn`도인가? 뒤쪽이면 콜백이 원시 텐서를 내줘야 한다.
3. **언어:** C++로 충분한가, 처음부터 C나 Python 바인딩이 필요한가?
4. **프로그램의 출력:** 첫 단계로 JSON 줄이면 충분한가?
5. **카메라 입력:** RTSP와 파일만인가, MIPI나 USB 카메라도인가? 잰 경로는 하드웨어 디코더에서 시작한다. 카메라의 원시 프레임은 RGA로 바로 들어가며, 여기서 잰 적이 없다.

## 제안하는 순서

1. librknnrt와 ffmpeg-rockchip의 라이선스를 읽고 "담을지 받을지"를 정한다. **완료:** [licences.ko.md](licences.ko.md).
2. C의 경로를 `core`에서 떼어 OpenCV 없는 라이브러리 타깃으로 만들고, 중단 대신 오류를 돌려주게 한다. `bench_main`의 동작은 그대로 두고, 기존 테스트와 스모크 실행으로 확인한다. **완료:** [lib/](../../lib/README.ko.md). 측정한 소스를 그대로 컴파일하는 별도 빌드다. 등록된 코드를 고치지 않았으므로 `bench_main`은 새로 확인할 것이 없었다.
3. 멈출 때까지 도는 모드, 재연결, 검출 콜백을 더한다. `bench_main`과의 동등성 테스트를 더한다. **완료:** [lib/](../../lib/README.ko.md)의 `rkzc::Detector`. 동등성 테스트는 등록된 `tools/demo_detect`와 비교한다. `demo_detect`는 검출 결과를 파일로 쓰고, `bench_main`은 개수만 기록하기 때문이다.
4. `rkzc-detect`와 서비스 파일을 쓴다.
5. 패키징 스크립트를 쓴다. `copyright` 파일과 ffmpeg-rockchip의 소스 압축 파일을 포함한다. M3가 설정을 시험한 것처럼, 초기화한 보드에 `.deb`를 설치해 본다.
6. 패키지한 경로를 잴지 정하고, 잰다면 계획을 등록한다.

각 단계는 PR 하나씩이다.
