# 공유 코어와 `bench_main` (M1-1)

`bench_main`은 변형 하나를 채널 수 하나로 실행하고, PROTOCOL §7이 정의한 기록을 남긴다. 이 문서는 빌드와 실행 방법, 출력 내용, [M1-1 확인](#m1-1-확인) 결과를 다룬다. 영문판과 다르면 영문판을 따른다.

## 빌드와 실행

```sh
tools/deploy_board.sh            # 작업 트리를 보드로 복사해 보드에서 빌드한다
# 보드에서 root로 실행한다(NPU 부하를 debugfs에서 읽는다):
sudo ./build/bench_main --variant C --channels 4 --source 'rtsp://<server>:8554/ch{n}'
```

| 옵션 | 기본값 | 의미 |
|---|---|---|
| `--variant` | (필수) | `none`(디코딩만) 또는 `C`. B와 A는 M1-2에서 추가한다 |
| `--channels` | (필수) | 1–32 |
| `--source` | (필수) | `rtsp://…/ch{n}` 또는 로컬 파일. 파일도 스트림처럼 원래 프레임 속도로 읽는다. `{n}`은 1…N으로 바뀐다 |
| `--condition` | `main` | `main`: 6번째 프레임마다(5 fps), `aux`: 매 프레임(30 fps) |
| `--warmup`, `--duration` | 20, 120 | 초(PROTOCOL §8) |
| `--model` | `models/yolov8n_i8.rknn` | |
| `--out` | `results/<run kind>/<UTC>_<variant>_<N>ch` | |
| `--run-kind`, `--repetition`, `--freeze-commit` | `check`, 1, `none` | 머리말에 기록한다(PROTOCOL §1) |

## 동작

구조는 PROTOCOL §5.1과 §8이 정한다.

- **스레드:** 채널마다 디코더 스레드가 하나 있고, 샘플러도 여기서 돈다. Q1은 2 × 채널 수만큼 담고, 가득 차면 가장 오래된 항목을 버린다. 전처리 스레드 2개가 슬롯을 받아 `prepare`를 실행한다. Q2는 6개를 담는다. NPU 워커 3개가 NPU 코어 0, 1, 2의 컨텍스트를 하나씩 맡아 `bind → rknn_run → 후처리`를 실행한다. 입력 슬롯은 11개다.
- **affinity:** 어떤 라이브러리도 스레드를 만들기 전에 프로세스를 cpu4–7에 고정한다. 그 뒤 계측 스레드만 cpu0으로 옮긴다.
- **디코더:** `h264_rkmpp`, DRM PRIME, `extra_hw_frames=8`, AFBC 끔. RTSP는 TCP로 읽고, 소켓 시간 제한은 5초다. MPP 입력 큐가 가득 차면 패킷을 버리지 않고 보관했다가 다시 보낸다.
- **SPS/PPS는 스트림 안에 있어야 한다.** `h264_rkmpp`는 이 정보를 스트림 안에서만 받는다. `h264_mp4toannexb` 필터가 mp4 입력에는 끼워 넣지만, 보통 SDP로 전달되는 RTSP에는 넣지 않는다. 이 정보가 없으면 프레임을 하나도 내놓지 않는다. 그래서 `stream-server/prepare_videos.sh`는 `repeat-headers=1`로 인코딩한다.
- **버퍼별 캐시**(`src/preprocess/fd_cache.h`, PROTOCOL §8): 채널과 디코더 버퍼 풀마다 dma-buf inode를 키로 하며, 디코더의 버퍼 수인 38개로 제한한다. 채널의 풀이나 프레임 크기가 바뀌면 그 채널의 항목을 퇴역시킨다. 퇴역한 항목은 다시 쓰지 않고 종료할 때 해제한다. 이전 풀의 프레임이 아직 처리 중일 수 있기 때문이다.
- **변형 C:** 스파이크의 경로다(docs/notes/spike.ko.md, AMENDMENTS A1). 시작할 때 컨텍스트마다 CPU가 바인딩된 NPU 출력을 정합적으로 읽는지 확인한다. 먼저 검은 슬롯을 실행해 출력 버퍼에 다른 데이터가 들어 있게 한 뒤, 114 회색 슬롯을 실행한다. 그 출력은 같은 회색 입력에 대한 `rknn_outputs_get` 결과와 비트 단위로 같아야 한다.

## 출력

모든 CSV는 `# key: value` 머리말로 시작한다. 시작 시각, NTP 상태, `prereg-v1`과 `freeze-m1` 커밋, 실행 종류, 모델 SHA-256, 디코더, 변형, 채널 수, 조건, 반복 번호, 코드 커밋, 최신 수정 항목이 들어간다.

| 파일 | 내용 |
|---|---|
| `frames.csv` | 처리한 프레임마다 한 줄: 채널, 디코딩 순서 번호, PTS, t0…t4(시작 이후 ns), 슬롯 대기, 컨텍스트, 슬롯, 검출 수 |
| `samples.csv` | 1초마다 한 줄: 코어별 NPU 부하, 모든 열 영역 온도, CPU/DDR/NPU 클럭, RSS, 채널별 디코딩 프레임 수 |
| `channels.csv` | 채널별 측정 구간 값: 디코딩 프레임 수와 속도, 드리프트(§7.6), 디코더 드롭(§7.6), 샘플링 프레임 수, Q1 드롭, 추론 속도(§7.4) |
| `threads.csv` | 측정 구간 끝에 살아 있는 스레드별 CPU 초, 이름, affinity. 그 전에 끝난 스레드는 `process_cpu_unattributed_s`에만 나타난다 |
| `summary.csv` | 프로세스 CPU와 클러스터별 분할(§7.1), 코어별·클러스터별 시스템 CPU(§7.2), 드롭률(§7.5), 지연·MPP 보유 시간·슬롯 대기 백분위수(§7.3), RSS, 클럭 범위, 최고 온도 |
| `env.json` | 머리말, 인자, 모든 스레드의 affinity, 큐 크기, 디코더 옵션, librga와 RKNN 버전, 바인딩 경로 |

§7.2의 유휴 기준선은 세션마다 한 번 재는 값이라 실행 결과에는 들어가지 않는다.

## M1-1 확인

2026-10-30에 다음 조건으로 실행했다.

- **송출 서버:** 보드 자체에서 돌렸다(mediamtx, localhost). docs/notes/spike.ko.md의 20초 테스트 클립을 반복한다. PROTOCOL §3의 별도 유선 송출 서버는 아직 구성하지 않았다.
- **거버너:** 기본값
- **빌드:** 이 커밋의 작업 트리. 결과 머리말에는 `6243d2a…-dirty`로 나온다.

- **출력 점검:** 시작할 때 C의 출력 정합성 점검이 세 컨텍스트 모두 통과했다.
- **디코더 버퍼:** 채널마다 디코더가 최대 7개를 썼고, 퇴역한 항목은 없었다.
- **디코딩만 할 때의 CPU:** 채널당 코어 하나의 약 4%다. 그중 채널의 디코더 스레드(RTSP와 ffmpeg)가 약 2.5%, MPP 파서가 1.2%, MPP HAL이 0.4%다. 기본 거버너의 낮은 A76 클럭에서 잰 값이고, B와 C가 똑같이 부담한다.
