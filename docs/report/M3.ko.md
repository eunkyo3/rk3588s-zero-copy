# M3 보고서: 초기화한 보드에서 M1의 H1 지점을 명령 하나로 재현

**M3가 무엇인가:** 깨끗한 이미지에서 스크립트 두 개로 M1의 H1 지점을 다시 잴 수 있는지 확인한다. 같은 NanoPi R6C를 공장 초기화하고, `scripts/setup_board.sh`로 설정한 뒤 `scripts/reproduce_m1.sh`로 쟀다. 지점, 기준, 순서는 어떤 실행보다 먼저 등록했다([prereg/M3.md](../../prereg/M3.ko.md), [A15](../../prereg/AMENDMENTS.ko.md)).

**결과(M3 §2): 재현됨.** 초기화 뒤의 네 값이 모두 M1의 ±10% 안이다.

| | M1 | 초기화 뒤(`m3_after`) | (M3 − M1) / M1 | ±10% 안 |
|---|---|---|---|---|
| B 프로세스 CPU | 43.283 s | 44.433 s | +2.66% | 예 |
| B 지연 p50 | 33.117 ms | 35.722 ms | +7.86% | 예 |
| C 프로세스 CPU | 18.560 s | 19.490 s | +5.01% | 예 |
| C 지연 p50 | 30.340 ms | 28.569 ms | −5.84% | 예 |

각 값은 주 조건 8채널에서 120초 창 3회 실행의 평균이다. 아래 표는 모두 `tools/m3_report.py`가 만든 [M3_tables.md](M3_tables.md)에서 왔다.

- **B의 p50은 약한 시험이다.** 계획서가 미리 밝혔다(M3 §2). M1의 세 값부터 크게 흩어져 있다. 계획서의 어림 계산으로는, 아무것도 바뀌지 않아도 새 3회 평균이 ±10%를 벗어날 확률이 약 37~47%였다. 이번에는 벗어나지 않았다. 벗어났더라도 그것만으로는 말해 주는 것이 적었을 것이고, 통과한 것도 마찬가지다.
- **M3는 H1을 다시 판정하지 않는다**(§7). 이 보드에서 깨끗한 이미지부터 M1의 숫자까지 가는 과정을 되풀이할 수 있다는 것을 말한다.

## 초기화와 설정

- **초기화:** 먼저 `m3_before`의 기록을 보드 밖으로 옮기고 SHA-256을 대조했다. 그다음 FriendlyElec의 `firstboot -r`이 data 파티션을 지웠다.
- **초기화 뒤의 보드:** `rom-version` 20251222, Ubuntu 24.04.3이고, A15의 판정 파일은 하나도 없었다. 설정은 `fresh: yes`로 기록했다.
- **설정은 첫 시도에 통과했다.** 14분 8초 걸렸고, 실패한 시도는 없다.

  | 단계 | 시간 |
  |---|---|
  | 벤치 링크와 시간 | 1초 |
  | 스트림 PC: 키, 호스트 키, 영상 manifest, 시계 | 1초 |
  | 패키지: `apt-get update`, `upgrade`, 설치 | 434초 |
  | librknnrt 2.3.2와 RKNN 헤더 | 2초 |
  | ffmpeg-rockchip 빌드 | 362초 |
  | 모델 | 1초 |
  | 빌드 | 40초 |
  | 기록 | 6초 |

- **운영자가 손으로 한 일:**
  1. 보드에 로그인해 Wi-Fi에 연결했다(`nmcli dev wifi connect`). 초기화가 그 설정을 지우기 때문이다;
  2. 벤치 케이블을 2.5G 포트(`eth1`)에 꽂았다;
  3. 스트림 PC용 키와 호스트 키를 보드에 복사했다;
  4. `main`을 클론했다;
  5. [reproduce.md](../notes/reproduce.ko.md)의 두 명령을 냉각 방식, 실내 온도와 함께 실행했다.

  3~5번은 SSH로 했다. 설정 전에 보드에서 그 밖의 것은 바꾸지 않았다.
- **설명하지 못하는 것 하나:** 설정은 보드의 부팅 시각을 04:40:21로 기록했다. 초기화 77분 뒤다. 그 사이 보드는 네트워크에 없었으므로, Wi-Fi를 연결하기 전에 손으로 다시 켰는지는 알지 못한다.

## 보드에서 바뀐 것

- **고정한 키(M3 §4): 어느 세션에서도 다른 것이 없다.** 커널, 드라이버, librknnrt, librga, MPP, ffmpeg-rockchip, RKNN 헤더, 빌드 플래그, 모델이 M1과 같다.
- **`m3_before`:** 인벤토리의 모든 줄이 M1과 같다.
- **`m3_after`:** diff 20줄, 곧 키 10개가 다르다. 고정한 키는 없다.
  - `os`: Ubuntu 24.04.5 대 24.04.4;
  - libc6 `2.39-0ubuntu8.12` 대 `8.9`, 라이브러리 5개;
  - libX11, liblzma, zlib의 업데이트;
  - ffmpeg-rockchip의 libavutil의 SHA-256. libavcodec, libavformat, libswresample은 M1과 바이트까지 같다.

  등록 전 chroot 시험이 찾은 것과 같은 10개다(A15).
- **패키지, 초기화 전 대 후:** 273개의 버전이 다르고, 70개는 옛 보드에만 있으며, 새 보드에만 있는 것은 없다([M3_tables.md](M3_tables.md#packages-before-against-after-m3-6)). 대부분은 초기화 뒤가 더 새 버전이다. netplan과 fwupd 등 몇 개는 더 옛 버전이다. 옛 보드가 새 보드와 다른 곳에서 받은 것이다.

## 기술적 결과

여기 있는 것은 판정하지 않는다(M3 §6).

- **`m3_before` 대 M1:** B CPU +0.40%, B p50 +6.03%, C CPU +4.74%, C p50 +1.09%. §2의 계산을 적용하면 이것도 ±10% 안이다.
- **`m3_after` 대 `m3_before`:** B CPU +2.25%, B p50 +1.73%, C CPU +0.26%, C p50 −6.86%.
- **C의 CPU는 두 스윕 모두 M1보다 약 5% 높다**(18.56초 대 19.44초와 19.49초). 곧 이 차이는 초기화 전에 이미 있었다. M1.1도 이 지점에서 +5.0%였다(M3.md, Disclosure). 초기화가 만든 차이가 아니다.
- **초기화 뒤 C의 p50**은 실행 하나가 끌어내렸다. 2회차가 23.7 ms이고 나머지는 31.2, 30.8 ms다. 표준편차는 4.2 ms로, 초기화 전의 0.4 ms보다 크다. 이 지점에서는 도착 위상을 통제하지 않으며(M2 §3.1), M1의 B도 같은 종류의 흩어짐을 보였다.

## 타당성 위협

- **보드 하나, 하루.** 보드, 냉각, 스트림 PC, 영상이 M1의 것이다. 다른 보드나 다른 이미지는 다루지 않는다([#70](https://github.com/eunkyo3/rk3588s-zero-copy/issues/70)).
- **변형마다 3회.** 기준은 3회 평균을 3회 평균과 비교한다. 이 지점의 지연에서는 잡음이 큰 비교다(M3 §2).
- **실내 온도**는 두 스윕 사이에 다르고, 측정이 아니라 운영자가 읽은 값이다([#68](https://github.com/eunkyo3/rk3588s-zero-copy/issues/68)).
- **Ubuntu 패키지는 설치한 날의 것이다.** 다른 날의 설정은 다른 버전을 설치한다. 고정한 키가 움직이면 세션이 멈추고, 나머지는 보고만 한다.
- **커널, 드라이버, librga, MPP는 이미지가 제공한다.** 설정이 설치하지 않으므로, 나중의 FriendlyElec 이미지는 고정 키 확인에서 실패할 수 있다.
- **설정은 바깥 서버에 기댄다:** 이미지의 apt 미러, GitHub(rknn-toolkit2, ffmpeg-rockchip, 이 저장소의 모델 Release), 스트림 PC.
- **등록 전에** 같은 기본 이미지의 chroot에서 설정을 네 번 시험했고, 거기서 수정 하나가 나왔다(ffmpeg의 버전 문자열, A15). 초기화한 보드의 설정이 첫 실제 설정이었고, 고치지 않고 통과했다.

## M3가 말하지 않는 것(§7)

- **다른 보드에 대해:** 같은 보드를 초기화한 것이다.
- **더 새 버전에 대해:** librknnrt, librga, 커널, 드라이버는 설계상 M1의 것이다.
- **M1의 다른 결과에 대해:** H1의 지점만 재현했다. H2와 H3의 지점, 스윕, M1.1의 설계는 재현하지 않았다.
- **H1의 판정에 대해:** M3는 H1을 다시 판정하지 않는다.
