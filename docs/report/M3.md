# M3 report: M1's H1 point, reproduced with one command on a reset board

**What M3 is:** a check that M1's H1 point can be measured again from a clean image, by two scripts. The same NanoPi R6C was factory-reset, set up by `scripts/setup_board.sh`, and measured by `scripts/reproduce_m1.sh`. The point, the criterion and the order were registered before any run ([prereg/M3.md](../../prereg/M3.md), [A15](../../prereg/AMENDMENTS.md)).

**Outcome (M3 §2): reproduced.** After the reset, all four values are within ±10% of M1's.

| | M1 | After the reset (`m3_after`) | (M3 − M1) / M1 | Within ±10% |
|---|---|---|---|---|
| B process CPU | 43.283 s | 44.433 s | +2.66% | yes |
| B latency p50 | 33.117 ms | 35.722 ms | +7.86% | yes |
| C process CPU | 18.560 s | 19.490 s | +5.01% | yes |
| C latency p50 | 30.340 ms | 28.569 ms | −5.84% | yes |

Each value is the mean of 3 runs, per 120 s window, at 8 channels in the main condition. Every table below is from [M3_tables.md](M3_tables.md), which `tools/m3_report.py` generates.

- **B's p50 is a weak test,** as the plan said in advance (M3 §2). M1's own three values spread widely. By the plan's rough arithmetic, a mean of 3 new runs would have missed ±10% with a probability of about 37 to 47% even if nothing had changed. It did not miss here; that it passed says little on its own, as a miss would have.
- **M3 does not judge H1 again** (§7). It says that the chain from a clean image to M1's numbers can be repeated on this board.

## The reset and the setup

- **The reset:** `m3_before`'s records were copied off the board first, and their SHA-256 compared. Then FriendlyElec's `firstboot -r` wiped the data partition.
- **The board afterwards:** `rom-version` 20251222 with Ubuntu 24.04.3, and none of the fresh-board markers of A15. The setup recorded `fresh: yes`.
- **The setup passed at its first attempt,** in 14 min 8 s. There was no failed attempt.

- **What the operator did by hand:**
  1. logged in on the board and joined the Wi-Fi network (`nmcli dev wifi connect`), since the reset removes it;
  2. plugged the bench cable into the 2.5G port (`eth1`);
  3. copied the stream PC's key and host key to the board;
  4. cloned `main`;
  5. ran the two commands of [reproduce.md](../notes/reproduce.md), with the cooling and the room temperature.

  Steps 3 to 5 were done over SSH. Nothing else was changed on the board before the setup.
- **One thing I cannot account for:** the setup records the board's boot at 04:40:21, 77 minutes after the reset. The board was off the network in between, so I do not know whether it was restarted by hand before the Wi-Fi was joined.

## What changed on the board

- **Pinned keys (M3 §4): none differs,** in either session. The kernel, the drivers, librknnrt, librga, MPP, ffmpeg-rockchip, the RKNN headers, the build's flags and the model are M1's.
- **`m3_before`:** its inventory equals M1's in every line.
- **`m3_after`:** 20 lines of its diff, which are 10 keys, none of them pinned:
  - `os`: Ubuntu 24.04.5 against 24.04.4;
  - libc6 `2.39-0ubuntu8.12` against `8.9`, in 5 libraries;
  - libX11, liblzma and zlib, by their updates;
  - ffmpeg-rockchip's libavutil, by its SHA-256. libavcodec, libavformat and libswresample are byte-identical to M1's.

  These are the same 10 keys the chroot test found before registration (A15).
- **Packages, before against after the reset:** 273 differ in version, 70 are on the old board only, and none is on the new board only ([M3_tables.md](M3_tables.md#packages-before-against-after-m3-6)). Most are newer after the reset. A few are older, such as netplan and fwupd; the old board had taken them from somewhere the fresh one did not.

## Threats to validity

- **One board, one day.** The board, its cooling, the stream PC and the videos are M1's. A different board or a different image is not covered ([#70](https://github.com/eunkyo3/rk3588s-zero-copy/issues/70)).
- **Three runs per variant.** The criterion compares means of 3 with means of 3. For latency at this point, that is a noisy comparison (M3 §2).
- **The room temperature** differs between the sweeps and is the operator's reading, not a measurement ([#68](https://github.com/eunkyo3/rk3588s-zero-copy/issues/68)).
- **Ubuntu's packages are the install date's.** A setup on another day installs other versions. The pinned keys would stop a session if one of them moved; the rest is only reported.
- **The image supplies the kernel, the drivers, librga and MPP.** The setup does not install them, so a later FriendlyElec image may fail the pinned check.
- **The setup depends on outside servers:** the image's apt mirror, GitHub (rknn-toolkit2, ffmpeg-rockchip, this repository's model Release) and the stream PC.
- **Before registration,** the setup was tested four times in a chroot of the same base image, and one fix came from it (ffmpeg's version string, A15). The reset board's setup was the first real one, and it passed unchanged.

## What M3 does not tell (§7)

- **About another board:** it is the same board, reset.
- **About newer versions:** librknnrt, librga, the kernel and the drivers are M1's by design.
- **About M1's other results:** only H1's point is reproduced, not H2's or H3's points, the sweeps, or M1.1's designs.
- **About H1's verdict:** M3 does not judge H1 again.
