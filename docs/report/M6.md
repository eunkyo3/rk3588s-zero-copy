# M6 report: where C's saving comes from

**What M6 is:** eight arms of `bench_main` in one session at H1's point (8 channels, 5 inferences per second each, a 120 s window), built to take the difference between B and C apart. The arms, the three hypotheses, the metrics and the order were registered before any run ([prereg/M6.md](../../prereg/M6.md), [A17](../../prereg/AMENDMENTS.md)).

| Arm | What ran |
|---|---|
| B | `--variant B`: preprocessing on the CPU, then a CPU copy into the NPU's input |
| Bd | `--variant Bd`: B's conversion, written straight into slots the NPU reads |
| Rc | RGA3 converts as in C, into a buffer the CPU can read; the CPU copies it into the NPU's input |
| C | `--variant C`: the zero-copy path |
| By | B with its resize and colour conversion done by libyuv in place of OpenCV |
| Cp | `--variant C --post neon`: C with the package's post-processing |
| Cpf | Cp with its threads allowed every CPU (`--cores all`) |
| Ct | C with the thread CPU time of every `rknn_run` recorded (`--time-rknn on`) |

**Outcome: all three hypotheses are adopted.**

| Hypothesis | Value | Threshold | Spec-literal | Practical |
|---|---|---|---|---|
| **M6-H1:** Rc keeps at least 90% of C's saving against B, `(B − Rc) / (B − C)` | 0.9352 | ≥ 0.90 | **adopted** | **adopted** |
| **M6-H2:** Cpf uses at least 20% more process CPU than Cp, `(Cpf − Cp) / Cp` | 0.4780 | ≥ 0.20 | **adopted** | **adopted** |
| **M6-H3:** By uses at least 10% less process CPU than B, `(B − By) / B` | 0.2883 | ≥ 0.10 | **adopted** | **adopted** |

Each value is from the means of 3 runs of process CPU per 120 s window: B 44.010 s, Bd 42.543 s, Rc 20.903 s, C 19.303 s, By 31.320 s, Cp 18.767 s, Cpf 27.737 s, Ct 19.887 s. No result is *mixed*: on system CPU from `/proc/schedstat` the three values are 0.9303, 0.4226 and 0.2765. No flag is set: every arm has 3 runs that count, every channel ran at 5.000 fps in every run, no frame was dropped, and no CV of process CPU is above its limit (the highest are Cpf's 4.2% and By's 4.2%; B's is 0.8%).

**What the three say, in one line each:**

- **The conversion carries the saving.** Moving the resize and colour conversion to RGA3 saved 23.1 s of B's 44.0 s while the CPU still copied every tensor. Dropping the copy as well saved a further 1.6 s. H1's margin is modest: see "H1's margin" below.
- **Where the threads run costs as much as the package's excess.** With nothing changed but the allowed CPUs, `bench_main` used 47.8% more process CPU. M5's package as installed used 48.5% more than the same restricted to the A76 cores.
- **A faster CPU path narrows the gap but does not close it.** libyuv took 28.8% off B. C is 38.4% below By, against 56.1% below B.

Every table of this report is in [M6_tables.md](M6_tables.md), which `tools/m6_report.py` writes from the records; the values here are copied from it.

## Question 1: conversion or copy

The four cells, from the means. `B − C` is 24.707 s.

| | The CPU copies into the NPU's input | No CPU copy | Difference |
|---|---|---|---|
| Conversion on the CPU | B 44.010 | Bd 42.543 | `B − Bd` 1.467 s (5.9%) |
| Conversion on RGA3 | Rc 20.903 | C 19.303 | `Rc − C` 1.600 s (6.5%) |
| Difference | `B − Rc` 23.107 s (93.5%) | `Bd − C` 23.240 s (94.1%) | |

The shares are of `B − C`.

- **The conversion's move to RGA3** saved 23.1 s with the copy and 23.2 s without it.
- **The copy bundle** cost 1.5 s on the CPU's side and 1.6 s on RGA3's side. Their difference, `(B − Bd) − (Rc − C)`, is −0.13 s, 0.5% of `B − C`: no interaction that three runs can show.
- **The cells are bundles, not pure factors** (M6 §1). B's slot has no sync and Bd's a START/END(WRITE) pair; Rc's has a START/END(READ) pair and C's none; Bd and Rc use cached memory and C uncached. `Rc − C` holds the copy, its sync pair and whatever RGA3's driver does for a cached destination.

By thread group, in seconds:

| Difference | Decoder | NPU workers | Preprocessing | Threads' sum |
|---|---|---|---|---|
| `B − Rc` | −1.147 | −0.130 | 24.360 | 23.073 |
| `Bd − C` | −1.137 | −0.003 | 24.410 | 23.263 |
| `B − Bd` | 0.553 | 0.967 | −0.043 | 1.473 |
| `Rc − C` | 0.563 | 1.093 | 0.007 | 1.663 |

- **The preprocessing threads carry the conversion:** 24.4 s of B's 24.7 s in those threads go when RGA3 converts, in either column.
- **The copy shows in two places,** in both rows alike: about 1.0 s in the NPU workers, where the `memcpy` runs, and about 0.56 s in the decoder's threads, which do the same work in every arm. M1.1 saw the same two parts for `B − Bd` (0.71 s and 0.57 s) and [cpu_breakdown.md](../notes/cpu_breakdown.md) could not explain the decoder's. M6 shows that Rc has it too, and does not explain it either.
- **The decoder's threads use about 1.1 s more when RGA3 converts** (C 11.18 s against Bd 10.05 s; Rc 11.75 s against B 10.60 s). M6 has no arm that separates why.

### H1's margin

- **The value is 3.5 points above the threshold.** The plan put the ratio's standard error at about 1.7 points, with an sd of 0.67 s taken for Rc; Rc's sd here was 0.78 s.
- **Within r3 alone the ratio is 0.897,** below 0.90. Rc's process CPU rose through the session (20.19, 20.78 and 21.74 s at positions 3, 14 and 19) while C's stayed within 0.2 s. Three runs cannot tell a drift from scatter.
- **The paired difference `Rc − C`** is 1.60 s with a descriptive 95% interval from −0.56 to 3.76 s. So the cost of Rc's bundle is known to within a few seconds only, and "at least 90%" holds by the registered rule, not with room to spare.
- **What does not depend on that margin:** the conversion's part. `B − Rc` is 23.1 s with an interval from 20.3 to 25.9 s, and `Bd − C` 23.2 s with an interval from 22.3 to 24.2 s.

## Question 2: a faster CPU path

| | B | By | C |
|---|---|---|---|
| Process CPU (s) | 44.010 ± 0.364 | 31.320 ± 1.309 | 19.303 ± 0.091 |
| Preprocessing threads (s) | 24.673 ± 0.057 | 11.427 ± 0.366 | 0.307 ± 0.006 |
| — as a share of the arm's process CPU | 56.1% | 36.5% | 1.6% |
| Stage `prepare`, p50 (ms) | 5.152 | 2.379 | 1.679 |

- **`(B − By) / B` = 0.2883.** The paired difference `B − By` is 12.69 s, with a descriptive 95% interval from 9.11 to 16.27 s.
- **All of it is in the preprocessing threads:** they used 13.25 s less, 54% of what B's used.
- **C's saving against By is 38.4%** (`(By − C) / By`), against 56.1% against B. `By − C` is 12.02 s, with an interval from 8.86 to 15.18 s.
- **By is not B with the same output.** It passed A5's criteria against B, as C did against B in M1, and its tensors differ from B's (mean absolute error 1.51 levels; A17 has the table). On the held-out videos it passed pooled; on video ④ alone criterion (c) was at −2.12%.
- **What this is and is not** (M6 §2): one library called one way, with B's filter and thread count. It does not show the fastest CPU path, and B stays the registered reference: H1's verdict and M1's numbers stand.

## Question 3: what separated the package from C

| Step | Value | Next to it |
|---|---|---|
| C → Cp, the package's post-processing: `(Cp − C) / C` | −2.8% | M2, staggered: −6.07% |
| Cp → Cpf, no pinning: `(Cpf − Cp) / Cp` | +47.8% | M5: `(P − P4) / P4` = +48.5% |

- **Cp against C:** the paired difference is −0.54 s with an interval from −2.12 to +1.05 s, which includes zero. The NPU workers used 1.08 s less in Cp (6.59 s against 7.67 s), as M2 found; the decoder's threads used 0.53 s more, within their scatter.
- **Cpf against Cp:** the paired difference is 8.97 s (10.28, 9.12 and 7.51 s).

- **About 59% of the system's CPU seconds under Cpf were on the A55 cores** (17.4 of 29.3 s), against 9% under Cp. The A76 cores did less: 11.9 s against 18.7 s.

- **Cpf and P are alike, cluster by cluster,** and so are Cp and P4. This is across sessions and descriptive, without a verdict (M6 §7). P's and P4's `/proc/schedstat` values hold M5's measuring tool, about 1.45 s per window on cpu0; Cp's and Cpf's hold only the metrics thread, about 0.1 s.

- **What this answers:** M5's report left open why the package as installed used about 40% more than C. A rise of that size appears in `bench_main` from the placement alone. What else differs between Cpf and P (the build, the JSON lines and the socket, the service, being measured from outside) was not measured here (M6 §7).

## Threats to validity

- **One board, one image, one model, one point, one day.** File-backed RTSP streams at 1080p. The auxiliary condition was not run (M6 §7), so nothing here says how the four cells look at 5 channels and 30 fps ([#70](https://github.com/eunkyo3/rk3588s-zero-copy/issues/70)).
- **One session, three runs per arm.** The intervals are descriptive, from 3 pairs. Three orders cannot balance eight arms (M6 §4); every run's position is in the tables.
- **H1 was the expected result and its margin is small** (see "H1's margin"). M1.1 had already shown that the copy is a small part; M6 filled the one cell M1.1 could not.
- **H2 tests the scheduler on this board,** under this load, on this kernel. Cpf's value moved more between runs than Cp's (sd 1.16 s against 0.60 s), and can move with anything else that runs on the board. Every repetition's value was above the threshold by at least 18 points.
- **H3 is about one library called one way.** By's sd (1.31 s) is the largest of the eight; every repetition's value was above the threshold by at least 16 points.
- **By's output is not B's.** It passed A5's criteria, which allow a difference; see Question 2.
- **The cells are bundles** (M6 §1): no value here is a pure cost of "the copy".
- **Seen before `freeze-m6`:** one run of each arm with a 10 s window, whose values A17 lists (B 3.67 s, Bd 3.56 s, Rc 1.66 s, C 1.55 s, By 2.64 s, Cp 1.48 s, Cpf 2.31 s, Ct 1.66 s). The thresholds, the arms, the metrics and the validity rules were fixed by `prereg-m6`, before any of the new arms' code existed, and nothing that M6 §5 fixes changed because of the checks.
- **The checks were made three times** before `freeze-m6`, since their tools changed twice after a round; `src/` did not change between the rounds, and the earlier records are kept (A17).
- **A17's readings.** A17 fixed four readings of M6.md before any run: Rc's trace is judged on the arm's own sync calls, since MPP syncs its own buffers in every arm; M6 §5's sentence on Cpf's drops applies together with §2's rule; a threshold met exactly counts as met; the report computes latency and rates from `frames.csv`. None of them decided a verdict here: no frame was dropped and no value is near its threshold's exact boundary.
- **Not shown by a trace:** that Rc's two sync calls per frame are START(READ) and END(READ). The board's strace does not print the flags; the code shows them (A17).
- **Reviews.** The code and the tools were reviewed before the checks' last round. The last changes to the tools after that (the trace's comparison with C, the commit-time check, a file's renaming) and A17's text were not reviewed separately.
- **The room temperature** is the operator's report, once for the session ([#68](https://github.com/eunkyo3/rk3588s-zero-copy/issues/68)).
- **Kernel-side CPU** is covered only by system CPU. `/proc/schedstat` agrees with process CPU for all three hypotheses; `/proc/stat` cannot be read ([#59](https://github.com/eunkyo3/rk3588s-zero-copy/issues/59)).

## What M6 does not tell (§7)

- **The rest of the package's difference from C:** see Question 3.
- **A pure cost of the copy,** or what RGA3's driver does for a cached destination.
- **Anything at another point,** the auxiliary condition included.
- **The best possible CPU path,** or the CPU cost of other Rockchip pipelines ([#63](https://github.com/eunkyo3/rk3588s-zero-copy/issues/63)).
- **What `rknn_run` does with its CPU time** ([#60](https://github.com/eunkyo3/rk3588s-zero-copy/issues/60)).
- **Why the decoder's threads use more CPU when the CPU copies the tensor, and when RGA3 converts.** M6 saw both again and has no arm for either.
- **Anything new about H1's verdict:** M1's results are not judged again.
