# 사전 등록 M4: NMS가 없는 모델 (부록)

- **등록:** 이 파일은 M4의 두 단계 중 1단계이며 태그 `prereg-m4`를 받는다. 기준 시각은 GitHub Release `prereg-m4`의 `created_at`이다. 그 시각과 태그의 커밋 SHA를 `docs/notes/env.md`의 등록 표에 기록한다.
- **규범 문서:** 영문 파일이다. `M4.ko.md`는 번역이며, 둘이 다르면 영문이 우선한다.
- **변경:** 이 파일은 `prereg-m4` 이후 고치지 않는다. 이후의 변경과 §8이 나중에 정하는 값은 [AMENDMENTS.ko.md](AMENDMENTS.ko.md)에 A13 다음 번호로 적는다(§9).
- **기준:** [PROTOCOL.ko.md](PROTOCOL.ko.md) v1과 유효한 수정안(A1–A13)을 적용하며, 이 파일이 따로 정한 것은 예외다. 용어는 PROTOCOL과 [M2.ko.md](M2.ko.md)의 것을 쓴다.
- **가설이 없다.** M4는 서술형 부록이다. 무엇을, 어떻게 재고, 무엇을 보고할지를 측정 전에 고정한다. M4의 어떤 결과도 판정이 아니다. M1과 M2의 판정은 영향을 받지 않는다(§8 2단계).

## 공개: 이 등록 전에 본 것

- **M1, M1.1, M2:** 그 결과 전부.
- **[docs/notes/m4_exploration.ko.md](../docs/notes/m4_exploration.ko.md)의 탐색:** 정지 이미지 21장, 즉 모델 저장소의 `bus.jpg`와 양자화 이미지 20장으로 했다. 이 20장은 COCO val2017 이미지이므로([models/coco_subset_20.sha256](../models/coco_subset_20.sha256)), §2.1의 5,000장 안에 들어 있다. 이 등록 전에 그 INT8·FP32 출력과 탐지 결과를 보았다.
  - YOLOv10n 변환과 그 INT8 출력. 클래스 점수가 0.510, 0.894, 0.967에서 잘린다.
  - conf 0.25에서 INT8과 ONNX FP32 비교: 195개 일치, FP32에만 13개, INT8에만 11개.
  - 모델 저장소의 두 후처리, 그리고 모델 저장소 Python과 대조한 `yolov10_post`.
  - `yolov10_post`의 비용: conf 0.25에서 호출당 CPU 0.084 ms.
- **그 뒤에 정한 것:**
  - YOLOv10n의 후처리 규칙과 동점 순서(§2.3);

## 2. 정확도

### 2.1 데이터

- **이미지:** COCO val2017의 이미지 5,000장 전부(`val2017.zip`).
- **주석:** `annotations_trainval2017.zip`의 `instances_val2017.json`, CC BY 4.0.
- **출처:** 두 파일 모두 `images.cocodataset.org`에서 받는다. SHA-256은 `freeze-m4` 전에 고정한다(§8).
- **라이선스:** 이미지는 각자의 Flickr 라이선스를 따르며 재배포하지 않는다. 저장소에는 이미지 이름과 준비한 입력의 해시만 두고 이미지는 두지 않는다.
- **양자화 이미지와 겹침:** 두 모델의 양자화 이미지 20장이 5,000장 안에 있다(공개 절). 그래서 이 20장을 뺀 결과도 함께 낸다(§6).

### 2.2 입력

입력은 PC의 평가 이미지(§8 2단계) 안에서 한 번만 만든다. 두 모델과 두 정밀도가 모두 같은 픽셀로 돈다.

1. **디코딩:** `cv2.imread(path, cv2.IMREAD_COLOR | cv2.IMREAD_IGNORE_ORIENTATION)`, BGR. 디코딩한 크기는 `instances_val2017.json`의 그 이미지 `width`, `height`와 같아야 한다(§8 3단계).
2. **크기 조정:** `r = 640 / max(w, h)`, `w' = floor(w·r + 0.5)`, `h' = floor(h·r + 0.5)`를 float64로 계산한다. `INTER_LINEAR`로 `(w', h')`로 줄이거나 늘린다. `(w', h') = (w, h)`이면 크기를 바꾸지 않는다.
3. **레터박스:** 114로 채운 640×640 캔버스의 `left = (640 − w') // 2`, `top = (640 − h') // 2` 위치에 놓는다. 114는 PROTOCOL §5.2 레터박스와 Ultralytics가 쓰는 채움 값이다.
4. **저장:** 각 입력을 무손실 PNG로 쓴다. 매니페스트 항목은 바인딩 순서(HWC)대로 놓은 640×640×3 RGB 바이트의 SHA-256과 `w`, `h`, `r`, `left`, `top`이다. 매니페스트는 이미지 id 오름차순이다.

- **보드에서:**
  - 각 PNG를 디코딩해 RGB로 바꾸고, 그 바이트를 매니페스트와 대조한다.
  - 그다음 B가 슬롯을 바인딩하는 방식으로 바인딩한다(`CpuSlots`, NPU 코어 0, M1의 바인딩).
  - PNG는 묶음 단위로 보드에 복사하고, 묶음의 이미지를 다 돌리면 지운다.
- **PC에서:**
  - ONNX FP32는 같은 바이트의 RGB/255로 돈다.
  - onnxruntime의 CPU 실행 프로바이더를 `intra_op_num_threads = 1`, `inter_op_num_threads = 1`, 기본 그래프 최적화로 쓴다.
- **Ultralytics 검증과의 차이에는 다음이 있다:**
  - RKNN 모델의 입력 모양이 고정이라 입력은 항상 640×640이다. Ultralytics 검증은 직사각형 배치를 쓴다.
  - 조정된 크기는 위와 같이 반올림한다.
  - 공개된 값은 참고일 뿐이다(§5, §6).

### 2.3 mAP용 후처리

설정은 Ultralytics 검증 기본값인 conf 0.001, 이미지당 최대 300개다. 클래스 점수는 모델이 내는 그대로, 즉 시그모이드를 거친 값을 쓴다. YOLOv8n의 score-sum 출력은 쓰지 않는다.

- **YOLOv10n:** `yolov10_post`(`src/core/yolov10_post`), conf 0.001, `max_det` 300.
  - conf를 넘는 모든 (셀, 클래스) 쌍이 후보이고, 상위 300개를 남긴다.
  - 동점은 branch(stride 8, 16, 32), 셀(행 우선), 클래스 순서로 정렬한다.
  - 각 탐지는 자기 셀의 박스를 디코딩한다. NMS는 없다.
  - **YOLOv10 원본 규칙과의 관계:** 원본 규칙은 최고 점수가 높은 셀 300개를 고른 뒤 그 안에서 상위 300쌍을 고른다. 이 규칙은 300번째 점수에서 동점인 쌍을 빼고는 같은 쌍을 남긴다.
  - **YOLOv10 자체 검증기와의 관계:** 그 검증기는 임계값을 쓰지 않는다. conf 0.001은 0.001 이하의 점수만 버리며, INT8에서는 그런 점수가 0뿐이다(탐색 노트 2절).
- **YOLOv8n:** multi-label이며, Ultralytics 검증이 하는 방식에 가깝다.
  1. conf 0.001을 넘는 모든 (셀, 클래스) 쌍이 후보다.
  2. 후보를 점수순으로, 동점은 (branch, 셀, 클래스) 순서로 정렬하고, 앞의 30,000개를 남긴다(Ultralytics의 `max_nms`).
  3. 클래스별 탐욕적 NMS를 IoU 0.7로 돌린다. 그 순서대로 내려가면서, 앞서 남긴 같은 클래스 후보와의 IoU가 0.7을 넘는 후보를 지운다.
  4. 남은 것 중 앞의 300개가 결과다.
  - IoU는 모델 입력 좌표의 박스로 계산하며, 클래스 오프셋은 쓰지 않는다.
  - 이 규칙은 M4의 정확도 도구용으로 따로 작성한다. `core/yolov8_post.cpp`와 Cp의 파일은 바꾸지 않는다.
- **두 구현:** 각 규칙을 두 번 구현한다.
  - **C++:** 보드의 INT8 출력에 쓴다. `yolov10_post`와 정확도 도구의 YOLOv8n 규칙이다.
  - **Python:** 평가 이미지 안에서 FP32 출력에 쓴다. INT8 점수는 C++와 같은 식 `(q − zp) × scale`을 float32로 계산하므로, 두 구현이 같은 동점을 본다.
  - **`freeze-m4` 전 확인**(§8 3단계): 매니페스트의 처음 50장에 대해 덤프한 보드 INT8 출력으로, 두 구현은 같은 목록을 내야 한다. 개수와 순서, 클래스가 같고, 점수 차는 1e-6, 박스 차는 1e-3 px 이내여야 한다. 예외로 두는 쌍은 없으며, IoU가 0.7에서 1e-6 이내라서 생긴 차이만 예외로 하고 보고한다.
- **COCO 형식으로:**
  - 두 정밀도 모두 하나의 Python 함수로 바꾼다. 박스는 모델 입력 좌표다. `left`와 `top`을 빼고 `r`로 나눈 뒤 [0, w] × [0, h]로 자르고, `[x, y, width, height]`로 쓴다.
  - 클래스 `k`는 `instances_val2017.json`에서 `k`번째로 작은 카테고리 `id`에 대응한다.
  - 탐지는 이미지마다 규칙이 돌려준 순서대로 쓴다. 점수 내림차순이고, 동점은 규칙의 동점 순서다. pycocotools의 안정 정렬은 동점 사이에서 이 순서를 유지한다.
  - 보드 도구는 점수와 박스를 float32 값의 유효숫자 9자리로 쓰고, COCO json도 같게 쓴다. 더 반올림하지 않는다.
- **평가:** pycocotools `COCOeval`, `iouType` bbox, 기본 매개변수(이미지와 카테고리마다 maxDets 1, 10, 100), 5,000장 전체.

### 2.4 함께 재는 것: 파이프라인 설정

같은 INT8 패스에서, 보드의 출력을 파이프라인이 하는 방식으로도 후처리한다.
- **YOLOv8n:** Cp의 `NeonPost`와 `yolov8_post`로, 둘 다 conf 0.25와 NMS 0.45. 두 결과를 이미지마다 필드 단위로 비교해 다른 이미지 수를 보고한다. 평가하는 것은 Cp의 탐지다.
- **YOLOv10n:** `yolov10_post`, conf 0.25.

그 mAP는 파이프라인이 쓰는 설정의, COCO 정지 이미지에서의 정확도로 보고한다(§7). 공개값과는 비교할 수 없다.

### 2.5 패스

- **패스:** 모델과 정밀도마다 하나, 모두 4개.
  - **패스**는 매니페스트 순서로 5,000장을 끊김 없이 한 번 도는 것이다.
  - **보드 INT8 패스**는 root로, 클럭을 고정하고, NPU 코어 0에서 돈다.
  - **바인딩된 출력:** 보드 패스는 100장마다 한 장씩 바인딩된 출력을 `rknn_outputs_get`과 대조한다.
  - **결정성:** 각 보드 패스는 처음 50장의 출력을 §8 3단계의 덤프와 바이트 단위로 비교한다. 다른 장수를 보고하며, 이 때문에 패스가 무효가 되지는 않는다.
- **탐지 결과:** 각 패스의 탐지(이미지당 300개로 약 150만 개)는 압축해서 Release `data-m4-<pass>`에 보관한다. 그 SHA-256과 패스의 헤더는 `results/m4/`에 둔다.

## 3. 처리량

### 3.1 NPU 용량(`calib_npu`)

- **실행:** 한 세션에서 모델마다 `P_cap`(코어 3개, §1의 파이프라인 후처리 포함)과 코어 1개의 원시 한계를 3회씩 반복한다. 모두 12회다.
- **순서:**
  - 한 모델 안에서는 `P_cap`을 먼저, 원시 한계를 다음에 돈다.
  - 한 반복 안에서는 한 모델의 두 실행을 먼저 돈다. 먼저 도는 모델은 반복마다 바뀌며, YOLOv8n부터 시작한다.
- **텐서:** M1-3의 텐서 세트 `tensors_c.u8`(C가 준비한 프레임, SHA-256 `051d6f12662e0b8ef9b72f00f74f498683913c39f197deb42c34ac1a54340c67`, A7).
- **절차:** M1-3과 같다(PROTOCOL §6.2, §9). 클럭 고정, 유휴 기준선, 냉각 게이트, 창 앞뒤의 `calib_npu` 출력 확인.
- **보고:** `P_cap`, 원시 처리율, 평균 `rknn_run`과 후처리 시간, NPU 부하.
  - M1-3의 YOLOv8n 값을 참고로 함께 적는다. M1-3은 Cp가 아니라 M1의 `yolov8_post`를 썼다.

### 3.2 파이프라인

- **팔:** 둘 다 같은 바이너리의 PROTOCOL §5.2 C다. 모델과 그 후처리만 다르다.
  - **C8:** YOLOv8n과 Cp의 후처리(`--variant C --post neon`). M2의 팔 Cp다.
  - **C10:** YOLOv10n과 `yolov10_post`(`--variant C --post v10`).
- **측정점:** M2의 두 점.
  - **주:** 8채널 × 5 fps, 엇갈림 샘플러(M2 §3.1).
  - **보조:** 5채널 × 30 fps.
- **반복:** 측정점마다 3회, 모두 12회.
- **포화:** 채널 × fps ≤ 0.8 × 그 모델의 `P_cap`일 때만 그 모델에 대해 그 점이 비포화다(PROTOCOL §6.2). 즉 보조점은 `P_cap` ≥ 187.5, 주점은 ≥ 50이어야 한다.
  - 먼저 도는 `calib_npu` 세션(§3.1)의 중앙값으로 정한다.
  - 어떤 모델에 대해 비포화가 아닌 점도 돌린다. 그 실행에는 포화 표시를 붙이고, PROTOCOL §9.3 규칙 3을 적용하지 않으며, 그 점의 비교는 서로 다른 부하 사이의 비교로 보고한다.
- **지표:** M2 §3.2와 같다.
  - 프로세스 CPU와 그 클러스터별 분할;
  - `/proc/schedstat`의 시스템 CPU와 `/proc/stat`의 시스템 CPU;
  - 지연 p50·p99, 드롭률, 추론률;
  - 단계 시간: `rknn_run`(`t2`–`t3`)과 후처리(`t3`–`t4`);
  - 주점에서 도착 위상과 엇갈림 오차.
- **차이:** 지표와 측정점마다 세 쌍의 차 `C10_r − C8_r`, 그 평균, 서술적 95% t 구간(자유도 2). 프로세스 CPU와 시스템 CPU는 `(C10_r − C8_r) / C8_r`도 낸다.
  - 무효 ×2 실행이 있는 반복은 빠진다.
  - 쌍이 2개보다 적으면 구간을 내지 않는다.
  - 임계값도 판정도 없다.

### 3.3 세션과 유효성

- **세션:** M2 §5.3과 같다. 냉각 게이트, 유휴 기준선(`/proc/schedstat` 포함), 세션마다의 실내 온도를 포함한다.
- **블록:** 6회씩 두 블록, 주점이 먼저다. 블록 안에서 반복마다 팔 순서는 C8→C10, C10→C8, C8→C10이다. 한 반복의 두 실행을 서로 다른 세션으로 나누지 않는다.
- **유효성:** PROTOCOL §9.3, 그리고 프로세스 CPU의 CV가 10%를 넘으면 표시하는 규칙, §3.2의 포화 표시.
- **열 점검:** 하지 않는다. 클럭이 고정값 아래로 내려가면 §9.3 규칙 1이 잡는다.

## 4. 실행과 헤더

- **실행 종류:** `m4`, `results/m4/`에 쓴다. 정확도 패스, `calib_npu` 세션, 파이프라인 실행을 모두 포함한다.
- **헤더:** PROTOCOL §1.4의 필드와 다음:
  - `prereg-m4`와 `freeze-m4`의 커밋(`freeze-m4` 전에는 `none`);
  - 모델의 SHA-256과 그 후처리;
  - 정확도 패스는 입력 매니페스트의 SHA-256;
  - PC에서 도는 패스는 CPU 모델, 평가 이미지의 digest, 시계 동기화 상태(`w32tm /query /status`).
- **PC의 시계:** PC에서 도는 패스는 시작 시각을 호스트 시계에서 가져온다. 시작 전에 호스트 시계와 NTP 서버의 오프셋을 재서(`w32tm /stripchart /computer:time.windows.com /samples:3 /dataonly`) 기록한다. 그 오프셋이나 컨테이너 시계와 호스트의 차가 1초를 넘으면 시작하지 않는다.
- **순서 검사:** `tools/check_prereg_order.py`는 두 가지를 더 확인한다. 모든 `m4` 실행과 패스는 `freeze-m4` 뒤에 시작해야 한다. 헤더에 `prereg-m4`를 적은 모든 `check` 실행은 `prereg-m4` 뒤에 시작해야 한다.

## 5. 잘못될 수 있는 것과 그때 할 일

- **한 규칙의 두 구현이 다르면**(§2.3): `freeze-m4` 전에 원인을 찾아 고치고, 확인을 처음부터 다시 한다.
- **정확도 패스는 다음 중 하나라도 생기면 무효다:**
  - 도구가 비정상 종료하거나 보드가 리셋된다;
  - 입력 바이트가 매니페스트와 다르다;
  - 바인딩된 출력이 `rknn_outputs_get`과 다르다;
  - 모델의 SHA-256이 §1과 다르다.

  PROTOCOL §9.3 규칙 1과 4는 패스에 적용하지 않는다. 패스의 출력은 클럭이나 스트림 서버에 좌우되지 않기 때문이다. 무효 패스는 첫 이미지부터 한 번 다시 돌리고 둘 다 남긴다. 무효 ×2인 패스는 원인과 함께 빠진 것으로 보고하고, 그 모델의 INT8 − FP32는 보고하지 않는다.
- **`calib_npu` 실행:**
  - PROTOCOL §9.3 규칙 1·2에 걸리거나 출력 확인(A7)에 실패하면 무효이며, 한 번 다시 돌린다.
  - 유효한 실행이 3개보다 적은 측정은 유효한 실행의 중앙값을 쓴다.
  - 유효한 실행이 없으면 그 모델의 측정점에 "포화 여부 모름" 표시를 붙이고, §9.3 규칙 3을 적용하지 않는다.
- **FP32 mAP가 공개값과 크게 다르면:** 실패 기준이 아니다(§2.2).
  - **공개값:** YOLOv8n 37.3 AP@[.5:.95](Ultralytics 문서 `docs/en/models/yolov8.md`, 커밋 `18d4e7a`)와 YOLOv10n 38.5(THU-MIG/yolov10 README, 커밋 `453c6e3`). 모델 저장소의 ONNX가 정확히 이 체크포인트에서 내보낸 것인지는 알 수 없다.
  - **발동 조건:** 어느 모델이든 FP32 AP@[.5:.95]를 소수 첫째 자리로 반올림한 값이 공개값과 2.0점 넘게 다를 때.
  - **그때:** 코드와 데이터를 §2.1–§2.3에 비추어 확인하고, 무엇이 나오든 그 확인을 보고한다.
- **결함:** 코드나 데이터가 §2.1–§2.3의 글과 어긋나는 것, 또는 입력이나 파일의 SHA-256이 §8에서 고정한 값과 다른 것이다.
  - 이 파일이 고정한 설정은 결함이 아니며 바꾸지 않는다. 레터박스, 임계값, 상한, 동점 순서, COCOeval 매개변수가 여기에 든다.
  - `freeze-m4` 뒤에 다른 경로로 결함을 찾아도, 결과가 어느 쪽으로 움직이든 같은 규칙을 적용한다.
  - 결함은 수정안으로 고치고, 결함 있는 코드나 데이터를 쓴 패스와 실행은 모두 다시 돌린다(§9). 고치기 전의 결과는 `results/`에 남기고 다시 돌린 결과 옆에 보고한다.
  - `freeze-m4` 뒤에는 입력 준비, 정확도 도구, 평가 이미지를 이 밖의 이유로 바꾸지 않는다.
- **바뀐 오브젝트:** 고정한 소스로 빌드했는데 후처리 컴파일 오브젝트가 `freeze-m4`에서 고정한 것과 다르면, 돌리기 전에 그 빌드로 §8 3단계의 해당 확인을 다시 한다. 소스가 바뀐 경우는 §9를 따른다.

## 6. 보고

- **정확도:**
  - **표:** 두 모델의 INT8과 FP32에 대해, 5,000장 기준 AP@[.5:.95], AP50, AP75, AP small·medium·large, AR@100.
  - **양자화 비용:** 모델마다 INT8 − FP32.
  - **양자화 이미지 제외:** 모든 패스의 AP@[.5:.95]와 AP50을 나머지 4,980장(COCOeval의 `params.imgIds`)으로도 낸다. 주 결과는 5,000장 값이다.
  - **파이프라인 설정(§2.4):** 별도의 표.
  - **참고:** §5의 공개값. 다른 설정에서 얻은 값이라고 표시한다.
  - **함께:** 각 패스가 이미지당 남긴 탐지 수, 300번째 점수에서 동점이 얼마나 자주 생겼는지.

  - 모델마다 `P_cap`, 원시 처리율, 단계 시간;

- **확인:** §8 3단계의 결과와, §5로 발동된 모든 것.
- **릴리스:** `v0.4-m4`, 보고서 `docs/report/M4.md`.

## 7. M4가 말해 주지 않는 것

- **다른 이미지에 대해:** 이 정확도는 PC에서 준비한 COCO val2017 정지 이미지의 정확도다. 파이프라인의 입력은 RGA가 준비한 동영상 프레임이며, §2는 이것을 재지 않는다.
- **모델 일반에 대해:** 두 모델은 rknn_model_zoo가 내보낸 그대로이고, 같은 20장으로 양자화했다. 이 20장은 평가하는 5,000장 안에 있다(§2.1). 다른 내보내기, 양자화 세트, 툴킷은 다른 결과를 낼 수 있다.
- **어느 모델이 나은지:** M4에는 결정 규칙이 없고 그런 주장도 하지 않는다.

## 8. 단계와 나중에 정하는 값

1. **`prereg-m4`:** 이 파일.
2. **구현:**
   - **`bench_main`:** 새 옵션 `--post v10`. variant C이고 YOLOv10n 내보내기의 출력 6개를 가진 모델에 쓴다. `yolov10_post`를 conf 0.25, `max_det` 300으로 부르며, `env.json`에 기록한다. 기본값은 계속 M1의 후처리다.
   - **`calib_npu`:** Cp를 포함해 같은 후처리 선택. `--run-kind m4`와 M4의 헤더 필드를 받고 `results/m4/`에 쓴다. 세션 스크립트는 §3.1의 순서로 두 모델을 한 세션에서 돌린다.
   - **정확도:** 보드용 도구(§2.2, §2.3, §2.4)와, 평가 이미지 안에서 도는 입력 준비, Python 규칙, COCO 평가. 평가 이미지는 변환 이미지(`tools/model/Dockerfile`)에 고정 버전의 pycocotools를 더해 만든다.
   - **기록:** 실행 종류 `m4`, 그 헤더 필드, 순서 검사(§4).
   - **바꾸지 않는 것:** `core/yolov8_post.cpp`와 Cp의 파일.
   - **이전 실행:** 이 변경은 `freeze-m1`과 `freeze-m2` 뒤에 공유 코어를 바꾼다. M1, M1.1, M2의 실행은 M2 §7 2단계와 A12의 근거로 영향을 받지 않는다. 그 실행들은 태그로 남은 각자의 바이너리로 만들었고, 기본 경로와 팔 Cp의 경로는 전과 같이 돈다(3단계).
   - **기본 경로가 달라지는 점:** 옵션 해석, 그리고 헤더와 `env.json`에 M4 필드가 더해진다(§4). 그 밖의 동작은 바뀌지 않으며, 후처리는 3단계의 공유 함수를 거쳐 부른다.
3. **`freeze-m4` 전 확인**, 실행 종류 `check`. 각 실행은 `prereg-m4` 뒤에 시작하고 헤더에 그것을 적는다.
   - **데이터:**
     - `val2017.zip`과 `annotations_trainval2017.zip`의 SHA-256;
     - 5,000장 각각이 주석의 크기로 디코딩되는지;
     - 입력 매니페스트(§2.2);
     - 그 안의 양자화 이미지 20장, 이름과 SHA-256으로;
     - 보드 도구가 PNG 5,000장을 모두 매니페스트의 바이트로 디코딩하는지.
   - **규칙:** 처음 50장에서 각 규칙의 두 구현(§2.3). 덤프한 출력은 §2.5의 결정성 확인에 쓰도록 남긴다.
   - **연결:** `bench_main`과 `calib_npu`는 하나의 공유 함수로 후처리를 고른다. 확인 도구가 `tensors_c.u8`의 10프레임에 대한 NPU 출력으로 그 함수를 부른다. C10 설정에서는 정확도 도구가 `yolov10_post`를 conf 0.25로 직접 부른 결과와, C8 설정에서는 `NeonPost`를 직접 부른 결과와 탐지가 같아야 한다.
   - **기본 경로:** 기본값으로 C를 2채널, 주 조건에서 한 번 돌린다. `env.json`의 스레드, affinity, `queues`가 M1의 실행 `32_main_C_2ch_r1`과 같아야 한다(M2와 같음).
   - **팔:** 8채널, 주 조건, 엇갈림으로 각 팔을 한 번씩 돌린다. `frames.csv`는 M2의 샘플러 규칙을 따라야 하고, `env.json`에는 그 팔의 모델 SHA-256과 후처리가 기록돼야 한다.
   - **오브젝트:** `libcore` 안의 후처리 컴파일 오브젝트(`yolov10_post`와 공유 함수의 것 포함)와 정확도 도구의 YOLOv8n 규칙의 SHA-256. `yolov8_post.cpp`와 Cp 파일의 것은 A13의 값과 같아야 하며, 다르면 M4의 빌드로 M2 §4의 동등성 확인을 다시 한다.
   - **그 값:** 이 확인들의 CPU 값과 탐지는 보고한다. §8이 고정하는 것은 §5의 규칙을 거치지 않고는 이것 때문에 바뀌지 않는다.
4. **`freeze-m4`:** 아래 값을 담은 AMENDMENTS의 커밋에 태그를 단다. 그 Release의 `created_at`이 M4 실행의 기준 시각이다.

| 값 | 정하는 때 |
|---|---|
| M4의 코드 커밋, 각 팔의 옵션 값, 후처리 오브젝트의 SHA-256 | `freeze-m4` 전 |
| COCO 파일과 입력 매니페스트의 SHA-256 | `freeze-m4` 전 |
| 평가 이미지: 베이스 digest와 `pip freeze` | `freeze-m4` 전 |
| 3단계 확인의 결과 | `freeze-m4` 전 |
| 라이브러리 버전, 클럭, 냉각이 A7, A9, A10, A13과 다르면 그 값 | `freeze-m4` 전 |

5. **`freeze-m4` 뒤의 실행:** 정확도 패스(§2.5), `calib_npu` 세션(§3.1), 그다음 파이프라인 세션(§3.2, §3.3).

## 9. 수정안

- **번호:** M4의 수정안은 AMENDMENTS.md에 A13 다음 번호(A14, A15, …)로 적는다.
- **PROTOCOL §15를 적용한다.** `freeze-m1` 자리에 `freeze-m4`를, B와 C 자리에 C8과 C10을 넣는다.
  - `freeze-m4` 전에는 변경의 영향을 받는 측정을 처음부터 다시 한다.
  - 그 뒤에는 다음 중 하나라도 바꾸면 그것을 쓴 모든 M4 실행과 패스가 무효가 된다: 공유 코어, 디코더, C의 경로, 두 파이프라인 후처리 중 하나, §2.2와 §2.3의 정확도 도구(두 구현 모두), `calib_npu`와 그 세션 스크립트, 평가 이미지.
  - 영향을 받은 파이프라인 측정점은 두 팔 모두 완전한 블록으로 다시 돌린다(§3.3). 영향을 받은 `calib_npu` 세션은 통째로, 영향을 받은 정확도 패스는 다시 돌린다.
  - 대체된 실행과 패스는 `results/`에 남기고 보고한다.
- **릴리스:** `prereg-m4` 뒤의 모든 수정안은 각자의 Release `amend-A<n>`로 게시한다.
