# Pre-registration M4: an NMS-free model (appendix)

- **Registration:** this file is stage 1 of M4's two stages and gets the tag `prereg-m4`. Its reference time is the `created_at` of the GitHub Release `prereg-m4`. That time is recorded with the tag's commit SHA in the Registration table of `docs/notes/env.md`.
- **Normative text:** this English file. `M4.ko.md` is a translation; if they disagree, this file governs.
- **Changes:** this file is not edited after `prereg-m4`. Later changes, and the values that §8 fixes later, go to [AMENDMENTS.md](AMENDMENTS.md), numbered on from A13 (§9).
- **Base:** [PROTOCOL.md](PROTOCOL.md) v1 applies, with the amendments in force (A1 to A13), except where this file says otherwise. Terms are PROTOCOL's and [M2.md](M2.md)'s.
- **No hypotheses.** M4 is a descriptive appendix. It fixes what is measured, how, and what is reported, before any measurement. No result of M4 is a verdict. M1's and M2's verdicts are unaffected (§8 step 2).

## 2. Accuracy

### 2.1 Data

- **Images:** all 5,000 images of COCO val2017 (`val2017.zip`).
- **Annotations:** `instances_val2017.json` from `annotations_trainval2017.zip`, under CC BY 4.0.
- **Source:** both files come from `images.cocodataset.org`. Their SHA-256 are fixed before `freeze-m4` (§8).
- **Licences:** the images keep their Flickr licences and are not redistributed. The repository holds their names and the hashes of the prepared inputs, not the images.
- **Overlap with the quantization images:** the 20 quantization images of both models are among the 5,000 (Disclosure). Results are also given without them (§6).

### 2.2 Inputs

The inputs are prepared once, on the PC, in the evaluation image (§8 step 2). Both models and both precisions run on the same pixels.

1. **Decoding:** `cv2.imread(path, cv2.IMREAD_COLOR | cv2.IMREAD_IGNORE_ORIENTATION)`, BGR. The decoded size must equal the image's `width` and `height` in `instances_val2017.json` (§8 step 3).
2. **Scaling:** `r = 640 / max(w, h)`, `w' = floor(w·r + 0.5)` and `h' = floor(h·r + 0.5)`, computed in float64. The image is resized to `(w', h')` with `INTER_LINEAR`. If `(w', h') = (w, h)` it is not resized.
3. **Letterbox:** the image is placed on a 640×640 canvas filled with 114, at `left = (640 − w') // 2` and `top = (640 − h') // 2`. 114 is the fill of PROTOCOL §5.2's letterbox and of Ultralytics.
4. **Storage:** each input is written as a lossless PNG. Its manifest entry is the SHA-256 of its 640×640×3 RGB bytes, in HWC order as bound, with `w`, `h`, `r`, `left` and `top`. The manifest lists the images by image id, ascending.

- **On the board:**
  - Each PNG is decoded and converted to RGB, and its bytes are checked against the manifest.
  - It is then bound as B binds its slots (`CpuSlots`, NPU core 0, M1's bindings).
  - The PNGs are copied to the board in chunks, and each chunk is deleted after its images have run.
- **On the PC:**
  - ONNX FP32 runs on RGB/255 of the same bytes.
  - It uses onnxruntime's CPU execution provider with `intra_op_num_threads = 1`, `inter_op_num_threads = 1` and the default graph optimization.
- **Differences from Ultralytics' val include:**
  - The input is always 640×640, because the RKNN model's input shape is fixed, where Ultralytics' val uses rectangular batches.
  - The scaled size is rounded as above.
  - The published values are context only (§5, §6).

### 2.3 Post-processing for mAP

The settings are Ultralytics' val defaults: conf 0.001 and at most 300 detections per image. The class scores are used as the models output them, after their sigmoid. YOLOv8n's score-sum outputs are not used.

- **YOLOv10n:** `yolov10_post` (`src/core/yolov10_post`), with conf 0.001 and `max_det` 300.
  - Every (cell, class) pair scoring above conf is a candidate, and the 300 best are kept.
  - Equal scores are ordered by branch (stride 8, 16, 32), then cell (row-major), then class.
  - Each detection decodes its own cell's box. There is no NMS.
  - **Relation to YOLOv10's own rule** (the 300 cells with the highest best score, then the 300 best pairs among them): it keeps the same pairs, except among pairs tied at the 300th score.
  - **Relation to YOLOv10's own validator,** which applies no threshold: conf 0.001 drops only scores at or below 0.001. In INT8 these are only the zeros (§2 of the exploration).
- **YOLOv8n:** multi-label, approximately as Ultralytics' val runs it.
  1. Every (cell, class) pair above conf 0.001 is a candidate.
  2. The candidates are ordered by score, with ties in (branch, cell, class) order, and the first 30,000 are kept (Ultralytics' `max_nms`).
  3. A greedy NMS per class then runs at IoU 0.7. Going down that order, a candidate is removed when its IoU with an earlier kept candidate of the same class is above 0.7.
  4. The first 300 kept are the result.
  - The IoU is computed on the boxes in model input coordinates, with no class offset.
  - This rule is written for M4's accuracy tool. `core/yolov8_post.cpp` and Cp's file are not changed.
- **Two implementations:** each rule is implemented twice.
  - **C++,** on the board's INT8 outputs, as `yolov10_post` and the accuracy tool's YOLOv8n rule.
  - **Python,** in the evaluation image, for the FP32 outputs. It computes INT8 scores with the C++ expression `(q − zp) × scale` in float32, so both see the same ties.
  - **Check before `freeze-m4`** (§8 step 3): on the board's dumped INT8 outputs of the first 50 images of the manifest, the two must give the same list. That means the same count and order, the same class, the score within 1e-6 and the box within 1e-3 px. No pair is excepted, except a difference caused by an IoU within 1e-6 of 0.7, which is reported.
- **To COCO:**
  - One Python function converts both precisions. The boxes are in model input coordinates. It subtracts `left` and `top`, divides by `r`, clips to [0, w] × [0, h], and writes `[x, y, width, height]`.
  - Class `k` maps to the `k`-th smallest category `id` in `instances_val2017.json`.
  - Detections are written per image, in the order the rule returns them: score descending, in the rule's tie order. pycocotools' stable sort keeps that order among equal scores.
  - The board tool writes scores and boxes as float32 printed with 9 significant digits, and the COCO json does the same, with no further rounding.
- **Evaluation:** pycocotools `COCOeval`, `iouType` bbox, with its default parameters (maxDets 1, 10 and 100 per image and category), over all 5,000 images.

### 2.4 Also measured: the pipeline's settings

In the same INT8 pass, the board's outputs are also post-processed as the pipeline runs them:
- **YOLOv8n:** through Cp's `NeonPost` and through `yolov8_post`, both at conf 0.25 and NMS 0.45. The two are compared field for field on every image, and the number of images where they differ is reported. Cp's detections are the ones evaluated.
- **YOLOv10n:** through `yolov10_post` at conf 0.25.

Their mAP is reported as the accuracy, on COCO still images, of the settings the pipeline uses (§7). It is not comparable with published values.

### 2.5 Passes

- **Passes:** one per model and precision, 4 in all.
  - **A pass** is one uninterrupted run over the 5,000 images, in manifest order.
  - **Board INT8 passes** run as root, with the clocks fixed, on NPU core 0.
  - **Bound outputs:** the board pass checks them against `rknn_outputs_get` on every 100th image.
  - **Determinism:** each board pass compares its outputs for the first 50 images, byte for byte, with the dump of §8 step 3. It reports how many differ; this does not invalidate the pass.
- **Detections:** each pass's detections (≈1.5 M at 300 per image) are kept compressed in a Release `data-m4-<pass>`. Their SHA-256 and the pass's header go under `results/m4/`.

## 3. Throughput

### 3.1 NPU capacity (`calib_npu`)

- **Runs:** in one session, for each model, `P_cap` (3 cores, with the pipeline's post-processing of §1) and the raw limit on 1 core, × 3 repetitions. That makes 12 runs in all.
- **Order:**
  - Within a model, `P_cap` comes first, then the raw limit.
  - Within a repetition, one model's two runs come first. The model that goes first alternates between repetitions, starting with YOLOv8n.
- **Tensors:** M1-3's tensor set `tensors_c.u8` (C's prepared frames, SHA-256 `051d6f12662e0b8ef9b72f00f74f498683913c39f197deb42c34ac1a54340c67`, A7).
- **Procedure:** as M1-3 (PROTOCOL §6.2, §9): fixed clocks, idle baseline, cooldown gate, and `calib_npu`'s output check before and after the window.
- **Reported:** `P_cap`, the raw rate, the mean `rknn_run` and post-processing times, and the NPU load.
  - M1-3's YOLOv8n values are given for reference. M1-3 used M1's `yolov8_post`, not Cp's.

### 3.2 Pipeline

- **Arms:** both are PROTOCOL §5.2's C, from the same binary. Only the model and its post-processing differ.
  - **C8:** YOLOv8n with Cp's post-processing (`--variant C --post neon`), which is M2's arm Cp.
  - **C10:** YOLOv10n with `yolov10_post` (`--variant C --post v10`).
- **Points:** M2's two.
  - **Main:** 8 channels × 5 fps, with the staggered sampler (M2 §3.1).
  - **Auxiliary:** 5 channels × 30 fps.
- **Repetitions:** 3 at each point, so 12 runs.
- **Saturation:** a point is unsaturated for a model only if channels × fps ≤ 0.8 × that model's `P_cap` (PROTOCOL §6.2). That means `P_cap` ≥ 187.5 for the auxiliary point and ≥ 50 for the main one.
  - The medians of the `calib_npu` session (§3.1), which runs first, decide.
  - A point that is not unsaturated for a model is still run. Its runs are labelled saturated, rule 3 of PROTOCOL §9.3 does not apply to them, and the comparison at that point is reported as between unequal loads.
- **Metrics:** as M2 §3.2:
  - process CPU, with its per-cluster split;
  - system CPU from `/proc/schedstat`, and `/proc/stat`'s system CPU;
  - latency p50 and p99, drop rate and inference rate;
  - stage times, with `rknn_run` (`t2` to `t3`) and the post-processing (`t3` to `t4`);
  - at the main point, the arrival phases and the stagger error.
- **Differences:** for each metric and point, the three paired differences `C10_r − C8_r`, their mean, and a descriptive 95% t interval (2 degrees of freedom). For process and system CPU, also `(C10_r − C8_r) / C8_r`.
  - A repetition with a run that is invalid ×2 drops out.
  - With fewer than 2 pairs, no interval is given.
  - There is no threshold and no verdict.

### 3.3 Sessions and validity

- **Sessions:** as M2 §5.3. That covers the cooldown gate, the idle baseline (with `/proc/schedstat`) and the ambient temperature per session.
- **Blocks:** two blocks of 6 runs, main first. Within a block, the arm order per repetition is C8→C10, C10→C8, C8→C10. The two runs of a repetition are not split across sessions.
- **Validity:** PROTOCOL §9.3, with its flag for a CV of process CPU above 10%, and §3.2's saturation label.
- **Thermal check:** none is run. Rule 1 of §9.3 catches any clock below its fixed value.

## 4. Runs and headers

- **Run kind:** `m4`, written under `results/m4/`. This covers the accuracy passes, the `calib_npu` session and the pipeline runs.
- **Header:** PROTOCOL §1.4's fields, plus:
  - the commits of `prereg-m4` and `freeze-m4` (`none` before it);
  - the model's SHA-256 and its post-processing;
  - for the accuracy passes, the input manifest's SHA-256;
  - for the passes on the PC, the CPU model, the evaluation image's digest, and the clock's sync state (`w32tm /query /status`).
- **The PC's clock:** a pass on the PC takes its start time from the host clock. Before it starts, the host clock's offset from an NTP server is measured (`w32tm /stripchart /computer:time.windows.com /samples:3 /dataonly`) and recorded. The pass does not start if that offset, or the container clock's offset from the host, is more than 1 s.
- **Order check:** `tools/check_prereg_order.py` also checks two things. Every `m4` run or pass starts after `freeze-m4`. Every `check` run whose header names `prereg-m4` starts after `prereg-m4`.

## 5. What could go wrong, and what then

- **The two implementations of a rule differ** (§2.3): the cause is found and fixed before `freeze-m4`, and the check is repeated in full.
- **An accuracy pass is invalid** if any of these happens:
  - the tool exits abnormally or the board resets;
  - an input's bytes differ from the manifest;
  - the bound outputs differ from `rknn_outputs_get`;
  - the model's SHA-256 differs from §1.

  Rules 1 and 4 of PROTOCOL §9.3 do not apply to passes, whose outputs do not depend on the clocks or the stream server. An invalid pass is repeated once from the first image, and both are kept. A pass that is invalid ×2 is reported as missing, with its cause, and that model's INT8 − FP32 is not reported.
- **`calib_npu` runs:**
  - A run is invalid under PROTOCOL §9.3 rules 1 and 2, or when its output check fails (A7), and is repeated once.
  - A measurement with fewer than 3 valid runs uses the median of its valid runs.
  - With none, the model's points are labelled "saturation unknown", and rule 3 of §9.3 does not apply to them.
- **FP32 mAP far from the published values:** this is not a failure criterion (§2.2).
  - **The published values:** YOLOv8n 37.3 AP@[.5:.95] (Ultralytics' documentation, `docs/en/models/yolov8.md` at commit `18d4e7a`) and YOLOv10n 38.5 (the THU-MIG/yolov10 README at commit `453c6e3`). Whether the zoo's ONNX files were exported from exactly these checkpoints is not known.
  - **The trigger:** either model's FP32 AP@[.5:.95], rounded to 0.1, differs from its value by more than 2.0 points.
  - **Then:** the code and data are checked against §2.1 to §2.3, and the check is reported whatever it finds.
- **Defects:** a defect is a departure of the code or data from the text of §2.1 to §2.3, or an input or file whose SHA-256 differs from the values fixed in §8.
  - A setting this file fixes is not a defect and is not changed. That covers the letterbox, thresholds, caps, tie order and COCOeval parameters.
  - The same rule applies to a defect found any other way, at any time after `freeze-m4`, whichever way it moves the results.
  - A defect is fixed by an amendment, and every pass or run that used the defective code or data is rerun (§9). The results before the fix stay under `results/` and are reported next to the reruns.
  - No other change is made to the input preparation, the accuracy tools or the evaluation image after `freeze-m4`.
- **Changed objects:** if a build from the frozen source gives post-processing objects that differ from those fixed at `freeze-m4`, the checks of §8 step 3 that cover them are repeated with that build before it runs. A change to the source falls under §9.

## 6. Reporting

- **Accuracy:**
  - **Table:** AP@[.5:.95], AP50, AP75, AP small, medium and large, and AR@100, for both models in INT8 and FP32, over the 5,000 images.
  - **Quantization cost:** INT8 − FP32 for each model.
  - **Without the quantization images:** AP@[.5:.95] and AP50 of every pass also over the 4,980 other images (COCOeval's `params.imgIds`). The 5,000-image values are the main ones.
  - **The pipeline's settings (§2.4):** in a separate table.
  - **Context:** the published values of §5, marked as obtained under other settings.
  - **Also:** how many detections per image each pass kept, and how often the 300th score was tied.
- **Throughput:**
  - `P_cap`, the raw rate and the stage times per model;
  - the pipeline metrics of both arms at both points, with their differences and intervals;
  - the saturation labels;
  - M4's C8 against M2's Cp (the same arm, another binary and session). This is exploratory, as M2 compared its C with M1's.
- **Checks:** the results of §8 step 3, and anything §5 triggered.
- **Release:** `v0.4-m4`, with the report `docs/report/M4.md`.

## 7. What M4 does not tell

- **About other images:** the accuracy is that of COCO val2017's still images, prepared on the PC. The pipeline's inputs are video frames prepared by RGA, which §2 does not measure.
- **About the models in general:** both models are as rknn_model_zoo exports them, quantized with the same 20 images, which are among the 5,000 evaluated (§2.1). Another export, calibration set or toolkit can give other results.
- **Which model is better:** M4 has no decision rule and makes no claim of one.

## 8. Stages and values fixed later

1. **`prereg-m4`:** this file.
2. **Implementation:**
   - **`bench_main`:** a new `--post v10`, for variant C and a model with the YOLOv10n export's six outputs. It calls `yolov10_post` with conf 0.25 and `max_det` 300, and is recorded in `env.json`. The default stays M1's post-processing.
   - **`calib_npu`:** the same choice of post-processing, including Cp's. It also gets `--run-kind m4` and M4's header fields, and writes under `results/m4/`. Its session script runs both models in one session, in §3.1's order.

   - **Unchanged:** `core/yolov8_post.cpp` and Cp's file.

## 9. Amendments

- **Numbering:** M4's amendments go to AMENDMENTS.md, numbered on from A13 (A14, A15, …).
- **PROTOCOL §15 applies** with `freeze-m4` in place of `freeze-m1`, and with C8 and C10 in place of B and C:
  - Before `freeze-m4`, measurements affected by a change are redone from scratch.
  - After it, a change to any of the following invalidates every M4 run or pass that used it: the shared core, the decoder, C's path, either pipeline post-processing, the accuracy tools of §2.2 and §2.3 (both implementations), `calib_npu` and its session script, or the evaluation image.
  - Affected pipeline points are rerun as complete blocks, for both arms (§3.3). An affected `calib_npu` session is rerun whole, and affected accuracy passes are rerun.
  - Superseded runs and passes stay under `results/` and are reported.
- **Releases:** every amendment made after `prereg-m4` is published as its own Release `amend-A<n>`.
