- **등록:** 2단계 중 1단계, 태그 `prereg-v1`. [HYPOTHESES.ko.md](HYPOTHESES.ko.md)와 함께 등록한다.

## 1. 등록과 일정

1. **1단계, `prereg-v1`:** 가설, 판정 규칙, 이 프로토콜. 어떤 측정보다 먼저 등록한다.
2. **2단계, `freeze-m1`:** AMENDMENTS.md가 §14의 모든 값을 담고 있는 커밋에 태그를 붙인다. 캘리브레이션(M1-3)과 동등성(M1-4) 이후, §12의 어떤 실행보다도 이전에 한다.
3. 각 단계의 **기준 시각**은 해당 GitHub Release의 `created_at`이다. 이 값은 태그의 커밋 SHA와 함께 `docs/notes/env.md`에 기록한다. `freeze-m1` 이후의 수정은 각자 별도의 Release를 가진다(§15).
4. 모든 결과 CSV는 다음을 담은 헤더를 가진다.
   - NTP 동기화된 시계의 ISO 8601 시작 시각(`timedatectl`의 동기화 상태를 기록한다)
   - `prereg-v1` 커밋 해시와 `freeze-m1` 커밋 해시(동결 전에는 `none`)
   - 실행 종류: `check`(M1-1/M1-2 기능 검사, §11.4, §3의 반복 재생 검사), `calibration`, `equivalence`, `comparison`, `reference`(A) 또는 `m1.1`
   - 모델 SHA-256, 디코더, 변형, 채널 수, 반복 번호
   - 해당 실행을 만든 코드의 커밋 해시, 그리고 그 시점에 유효한 최신 수정(없으면 `none`)
5. `tools/check_prereg_order.py`는 다음을 검사한다.
   - `results/` 아래의 모든 파일이 `prereg-v1` 이후에 시작했다.
   - 모든 `comparison`, `reference`, `m1.1` 실행이 `freeze-m1` 이후에 시작했다.
   - 헤더가 Release `amend-A<n>`(§15)으로 공개된 수정을 명시하는 모든 실행이 그 Release의 `created_at` 이후에 시작했다.

   파일 수정 시각은 쓰지 않는다.

## 2. 시험 대상 시스템

- FriendlyElec NanoPi R6C 한 대(RK3588S: Cortex-A55 4개 cpu0–3, Cortex-A76 2개 cpu4–5, Cortex-A76 2개 cpu6–7, 3코어 NPU), RAM 8 GB.
- FriendlyElec Ubuntu 이미지. `tools/collect_env.sh`가 매 실행 전에 커널, RKNPU 드라이버, librknnrt, librga, MPP, ffmpeg 버전, 클럭, 온도, NTP 상태를 기록한다. OpenCV 버전과 빌드 정보(`cv::getBuildInformation()`), `bench_main`의 컴파일러와 플래그도 기록한다. 버전, 빌드, 컴파일러와 플래그는 `freeze-m1`에서 동결한다(§14). OpenCV 빌드는 M1-2의 첫 B 실행 전에 AMENDMENTS에서 고정한다.
- 등록 시점에 관찰한 값(참고용이며 구속력 없음): Ubuntu 24.04.4, 커널 6.1.141, RKNPU 드라이버 v0.9.8, librknnrt 2.3.2, librga 1.10.3.
- 냉각 구성(방열판, 팬, 케이스)은 `freeze-m1`에서 고정하며 세션마다 주변 온도와 함께 기록한다.
- **세션:** §9.2의 10분 유휴 구간과 함께 시작한다. 보드가 재부팅되거나, 냉각 구성이 바뀌거나, 실행 없이 30분이 지나면 끝난다.

## 3. 입력 스트림

- 별도 PC가 RTSP 서버(mediamtx)를 실행하므로, 송출이 보드에 부하를 주지 않는다. 보드는 유선 이더넷으로 TCP를 통해 RTSP를 가져온다.
- 소스는 라이선스를 확인한 공개 영상이다. 각각 1920×1080 H.264, 30 fps, B-프레임 없음(`-bf 0`), GOP 30, 4 Mbps CBR로 재인코딩하며, 스트림에 limited range를 명시한다. 원본의 색 행렬(color matrix)을 기록한다.
- 각 채널은 영상 하나를 반복 재생하는 독립된 RTSP 경로다. 발행자(publisher)는 bench가 연결할 때 요청에 따라 시작하고 연결이 끊긴 뒤 멈추므로, 각 채널은 매 실행마다 영상의 처음부터 시작한다. 타임스탬프는 반복 재생 경계를 넘어서도 연속이다. `freeze-m1` 전에, 채널 대응에 들어 있는 모든 영상에 대해, 그 영상의 반복 재생 지점을 최소 두 번 넘는 1채널 `--variant none` 실행에서 디코더 드롭이 0임을 보여야 한다(§7.6).
- 채널과 영상의 대응은 `freeze-m1`에서 고정한다. 송출 서버의 로그는 모든 실행과 함께 저장한다.
- 동등성 검사(§11)와 캘리브레이션(§6.2)은 RTSP 대신 같은 인코딩의 로컬 mp4(`file_source`)를 읽는다.

## 4. 모델과 후처리

- YOLOv8n, COCO 사전 학습, 640×640 입력, INT8 RKNN 모델.
- 보드의 librknnrt와 정확히 같은 버전의 rknn-toolkit2로 변환한다. 정규화(평균 0, 표준편차 255)는 모델 안에 있으므로 입력 텐서는 uint8 RGB NHWC다. 양자화 데이터셋과 모델 SHA-256을 기록하며, 모델은 `freeze-m1`에서 동결한다.
- 후처리는 모든 변형에서 같은 코드다. YOLOv8 박스 디코딩, 신뢰도 임계값 0.25, IoU 임계값 0.45의 클래스별 NMS.

## 5. 시험 대상 파이프라인

### 5.1 공유 코어

바이너리 하나, `bench_main --variant {none,A,B,C}`. 모든 변형이 같은 단계를 쓴다.

```
decoder thread (1 per channel) → sampler → Q1 → preprocessing pool [acquire_slot → prepare] → Q2 → NPU workers [bind → rknn_run → post-process]
```

- **디코더:** [nyanmisaka/ffmpeg-rockchip](https://github.com/nyanmisaka/ffmpeg-rockchip)의 `h264_rkmpp`가 `AV_PIX_FMT_DRM_PRIME` 프레임을 만든다. `extra_hw_frames=8`과 디코더의 기본 버퍼 할당을 쓴다(사용자 정의 `hw_device_ctx` 없음).
  - ffmpeg-rockchip 빌드가 두 번 실패하면 jellyfin-ffmpeg의 rkmpp 디코더를 대신 쓰고 AMENDMENTS에 기록한다. 배포판의 ffmpeg 패키지는 쓰지 않는다.
  - 빌드, 그 커밋, 모든 디코더 옵션은 `freeze-m1`에서 동결한다. B와 C는 같은 빌드를 쓴다.
  - 디코더 버퍼가 CPU 캐시 대상인지는 스파이크에서 확인해 기록한다(§14). 이것은 B의 읽기 비용에만 영향을 주므로, 모든 결과와 함께 명시한다(HYPOTHESES, 판정).
- **샘플러:** 채널별 디코딩 순서 카운터. 본편 조건: `counter % 6 == 0`인 프레임을 샘플링한다(채널당 5 fps). 보조 조건: 모든 프레임을 샘플링한다(30 fps). 샘플링하지 않는 프레임은 즉시 해제한다.
- **Q1:** 깊이 `2 × channels`, 가장 오래된 것부터 버린다(drop-oldest). Q1만이 드롭하는 큐다.
- **전처리 풀:** K = 2 스레드. 각 스레드는 Q1에서 프레임을 꺼내 빈 입력 슬롯을 얻고(`acquire_slot`), `prepare`를 실행하며, `prepare`가 끝나는 즉시 DRM PRIME 프레임을 해제한다.
- **Q2:** 깊이 6.
- **NPU 워커:** 워커 3개. 각 워커는 NPU 코어 하나(0, 1, 2)에 고정된 RKNN 컨텍스트를 하나씩 소유한다. 워커는 `bind → rknn_run → post-process`를 인라인으로 실행한 뒤 슬롯을 반환한다. 컨텍스트마다 출력 세트가 하나씩 있다(`rknn_create_mem` + `rknn_set_io_mem`). 다음 `rknn_run`은 후처리가 끝난 뒤에만 시작하므로, 출력이 사용 중에 덮어써지지 않는다.
- **입력 슬롯:** B와 C 모두 N = 11(= K + depth(Q2) + 3).
- **컨텍스트 선택:** 늦은 바인딩. 워커는 Q2에서 아무 슬롯이나 가져와 자신의 컨텍스트에 바인딩한다.

### 5.2 변형

`prepare`, `bind`, 입력 슬롯 뒤의 메모리만 다르다.

- **B (CPU 복사):**
  - 슬롯은 CPU 메모리다.
  - `prepare`는 DRM PRIME fd를 `mmap`으로 매핑하고(버퍼별 캐시, §8) 프레임마다 `DMA_BUF_IOCTL_SYNC` START(READ)와 END(READ)를 각각 정확히 한 번씩 호출한다. `av_hwframe_map`은 쓰지 않는다.
  - 그다음 리사이즈를 먼저 하고 색 변환을 나중에 하여, 레터박스를 적용한 이미지를 슬롯에 기록한다.
  - `bind`는 `rknn_inputs_set`이다.
- **C (제로카피):**
  - 슬롯은 `system-uncached-dma32`(대체: `system-dma32`)의 640×640×3 uint8 dma-heap 버퍼다. 각각 `rknn_create_mem_from_fd`로 3개 컨텍스트 모두에 등록하며, 입력 속성은 UINT8/NHWC이다.
  - `prepare`는 가져온(imported) DRM PRIME 버퍼(버퍼별 캐시, §8)에서 슬롯으로 `IM_SYNC`와 함께 RGA `improcess`를 실행한다.
  - `bind`는 `rknn_set_io_mem`이다.
  - 스트리밍 중 CPU는 픽셀 데이터를 읽거나 쓰지 않는다. 슬롯 테두리는 초기화 때 한 번 기록한다. §11.4로 확인한다.
- **A (소프트웨어 디코딩, 참조):** libavcodec 소프트웨어 H.264 디코딩으로 CPU 메모리에 받은 뒤, B의 리사이즈, 색, 레터박스 코드와 B의 `bind`를 쓴다.
- **none (디코딩 전용):** 디코더와 샘플러만 쓴다. 샘플링된 프레임은 즉시 해제한다. 디코딩 전용 한계(§6.1)와 §11.4의 기준선으로 쓴다.
- **레터박스:** B와 C의 슬롯 테두리는 초기화 때 CPU `memset`으로 값 114로 한 번 채운다. `prepare`는 640×360 이미지 영역(1920×1080을 1/3로 축소, 수직 중앙 정렬)만 기록한다.

### 5.3 공정성 불변 조건

B와 C는 스레드 구성, 큐, 드롭 정책, 슬롯 수, 출력 바인딩, 후처리 위치, 계측, 버퍼별 캐시 정책이 동일하다. 모든 대체 경로(§5.4)는 둘 모두에 적용한다.

### 5.4 대체 경로 (사전 등록)

- **대칭 컨텍스트 대체 경로:** dma-buf 하나를 둘 이상의 컨텍스트에 등록할 수 없으면, B와 C **모두** `acquire_slot` 시점에 라운드로빈으로 컨텍스트를 고른다. 그러면 Q2는 깊이 2인 컨텍스트별 큐 3개(합계 6)로 나뉜다. N은 11을 유지한다.
- **해제 정책:** 한 컨텍스트에서 RKNN 메모리 객체를 해제하면 다른 컨텍스트의 실행이 깨지는 경우, 모든 RKNN 메모리 객체는 종료 시에만 해제하고, 그 뒤에 fd를 닫는다.
- **C 경로 대체:** §5.2의 C 경로가 동작하도록 만들 수 없으면, 대체 경로는 순서대로 C1(RGA가 `rknn_create_mem2`의 메모리에 기록), 그다음 ffmpeg의 `scale_rkrga` 필터다. 대체 경로는 프로젝트 소유자의 승인이 있을 때만 채택하며 `freeze-m1` 전에 AMENDMENTS에 기록한다. 이 경우 모든 C 결과에 해당 대체 경로를 표기한다.
- 사용 중인 경로는 AMENDMENTS(§14)와 각 실행의 `env.json`에 기록한다.

## 6. 채널 집합과 용량

### 6.1 디코딩 전용 한계 `L`과 본편 채널 집합

- **`L`:** `--variant none` 실행이 120 s 창 동안 모든 채널에서 수신 드리프트 ≤ 1 s와 디코더 드롭 0(§7.6)을 유지하면 *통과*한다. `L`은 M1-3에서 §10의 절차로 구하되, "유지" 대신 "통과"를 쓰고, 시작은 (`min(8, L)` 대신) 8채널, 상한은 `L` 대신 32채널로 한다. 이 실행들에는 §9.3의 4번 규칙을 무효 사유로 적용한다. 확정된 채널 수가 `L`이다.
- `L`은 송출 서버와 네트워크를 포함하므로, 모든 채널 스윕의 상한이다.
- **본편 집합:** `{1, 2, 4, 8, 12, 16}` 중 `L` 이하인 값, 그리고 `L` 자체가 집합에 아직 없으면 `L`도 추가한다.

### 6.2 파이프라인 용량 `P_cap`과 파생 값

- **`P_cap`:** `tools/calib_npu --with-post`로 측정한다.
  - 입력 텐서 1,000개 세트를 dma-heap 버퍼에 미리 올린다.
  - 워커 `w`(NPU 코어 `w`의 컨텍스트 하나, `w` = 0, 1, 2)는 인덱스 ≡ `w` (mod 3)인 텐서들을 순환한다. 각 텐서는 `rknn_create_mem_from_fd`로 해당 컨텍스트에 등록하고 `rknn_set_io_mem`으로 바인딩한다. 각 단계는 `rknn_run`과 실제 출력에 대한 실제 후처리를 실행한다.
  - `prepare`도 CPU 복사도 없으므로 `P_cap`은 두 변형 모두의 상한이다. 두 변형에 같은 값을 쓴다.
  - `P_cap` = 20 s 워밍업 뒤 120 s 동안 완료된 추론 수를 120으로 나눈 값. 3회 실행의 중앙값.
  - 텐서 세트는 M1-3 시작 시 `file_source` 영상에서 `tools/dump_tensor`로 덤프하며, 생성 경로를 기록한다.
- 원시 NPU 한계(`rknn_run`만, 1, 2, 3코어)도 기록하며, 참고용일 뿐이다.
- **비포화 조건:** 채널 ≤ `L` **이고** `channels × 추론 fps ≤ 0.8 × P_cap`. 추론 fps는 5(본편) 또는 30(보조)이다.
- **H2 보조 지점:** `floor(0.8 × P_cap / 30)` 채널. 0이면 보조 지점은 없다.

### 6.3 그 밖의 집합

- **보조 집합:** `{1, 2, 3, 4, 5} ∪ {H2 보조 지점}`.
- **A 집합:** `{1, 2}`, 본편 조건.

## 7. 지표

모든 시각은 `CLOCK_MONOTONIC`을 쓴다. 측정 창은 20 s 워밍업 뒤의 120 s다.

### 7.1 프로세스 CPU (H1 주 지표)

- 창 동안 bench 프로세스의 Δ(utime + stime)를 `/proc/<pid>/stat`에서 구해 CPU-초로 나타낸다. 모든 스레드를 포함한다.
- 클러스터별 내역은 `/proc/<pid>/task/<tid>/stat`에서 구하며, 각 스레드의 친화도(affinity, §8)에 따라 귀속시킨다. 파이프라인 스레드(cpu4–7)는 A76으로, 계측 스레드(cpu0)는 A55로 세고, 그 밖의 친화도를 가진 스레드는 미귀속으로 센다.

### 7.2 시스템 CPU (H1 보조 지표)

- `/proc/stat`의 CPU별 Δ 비유휴 시간(비유휴 = user + nice + system + irq + softirq + steal)을 CPU-초로 나타낸다. CPU별, 클러스터별(cpu0–3, cpu4–5, cpu6–7), 합계로 보고한다. 커널 스레드(드라이버 작업, 인터럽트)는 §7.1이 아니라 여기에 나타난다.
- **유휴 차감:** 실행의 값에서 유휴 기준선을 뺀 값. 기준선은 파이프라인을 실행하지 않은 상태에서 120 s 동안 같은 양을 측정한 것이며, 세션마다 한 번 측정한다.

### 7.3 지연

처리된 프레임마다의 타임스탬프:

| 이름 | 시점 |
|---|---|
| t0 | 디코더가 프레임을 반환(`avcodec_receive_frame`) |
| t1 | `prepare` 시작 |
| t2a | `prepare` 완료, DRM PRIME 프레임 해제 |
| t2b | `bind` 시작(NPU 워커에서) |
| t2c | `bind` 완료 |
| t3 | `rknn_run` 반환 |
| t4 | 후처리 완료 |

- **종단 간 지연:** 처리된 프레임에 한해 `t4 − t0`. Q1에서 드롭된 프레임은 대신 드롭률에 센다.
- **MPP 보유 시간:** `t2a − t0`. **슬롯 대기:** `acquire_slot`에서 보낸 시간.
- **p50 / p99:** 실행마다, t4가 창 안에 있는 모든 채널의 처리된 모든 프레임에 대해 `numpy.percentile`의 기본(선형) 보간으로 구한다.

### 7.4 추론 속도

채널마다: t4가 창 안에 있는 그 채널의 프레임 수를 120 s로 나눈 값.

### 7.5 드롭률

창 동안 Q1 드롭 수를 샘플링된 프레임 수로 나눈 값. 모든 채널을 합친다.

### 7.6 수신 드리프트와 디코더 드롭

- 채널별 **드리프트:** `D(t) = (30 × (t − t_w) − frames returned by the decoder in [t_w, t]) / 30` 초. `t_w`는 창의 시작이다. `D(t)`는 1초 샘플(§7.7)마다, 그리고 창의 끝에서 평가한다. 채널의 드리프트는 이 값들 중 최댓값이다.
- 채널별 **디코더 드롭:** 창 안에서 반환된 프레임(`t_w` 직전에 반환된 마지막 프레임으로부터의 간격 포함)에 대해 다음을 센다.
  - PTS 간격이 ≤ 0이거나 프레임 주기의 1.5배를 넘는 경우마다 빠진 프레임 `max(1, round(Δ / period) − 1)`개로 센다.
  - `AV_FRAME_FLAG_CORRUPT`이거나 `decode_error_flags`가 0이 아닌 프레임마다 하나로 센다.
  - `EAGAIN`이나 `EOF`가 아닌 디코더 오류 반환마다 하나로 센다.

### 7.7 1초 샘플

cpu0의 계측 스레드가 1초마다 다음을 샘플링한다.

- 코어별 NPU 부하(`/sys/kernel/debug/rknpu/load`)
- 모든 thermal zone의 온도
- CPU 정책 0, 4, 6, DDR(`dmc`), NPU devfreq의 현재 주파수
- bench 프로세스의 VmRSS
- 채널마다, 지금까지 디코더가 반환한 프레임 수

### 7.8 보고

모든 측정 지점은 유효 실행에 대해 각 지표의 평균과 표준편차를 보고한다.

## 8. 실행 설정

별도 언급이 없으면 B와 C가 동일하다.

- 워밍업 20 s, 측정 120 s, 측정 지점마다 3회 반복.
- CPU 정책 0, 4, 6, DDR(`dmc`), NPU devfreq의 거버너를 `tools/set_perf_mode.sh`로 `performance`에 설정한다. 그 결과로 고정된 주파수를 M1-3에서 sysfs로 읽어 AMENDMENTS에 기록한다. 이후의 모든 실행은 이 값과 대조해 검사한다(§9.3 1번 규칙).
- **친화도:** 프로세스 친화도를 어떤 라이브러리도 초기화되기 전에 cpu4–7로 설정하여, 라이브러리 스레드(MPP, librknnrt, ffmpeg)가 이를 상속하게 한다. 그다음 계측 스레드가 스스로 cpu0으로 옮겨 간다. 모든 스레드의 친화도를 기록한다. `cv::setNumThreads(1)`.
- `rknn_init` 플래그는 B와 C가 동일하다. 동기 실행만 쓰고(`RKNN_FLAG_ASYNC_MASK` 없음, 논블로킹 실행 없음), `RKNN_FLAG_DISABLE_FLUSH_*` 플래그는 하나도 쓰지 않는다. 정확한 플래그를 기록한다.
- K = 2, Q1 = 2 × channels, Q2 = 6(§5.4의 대체 경로에서는 컨텍스트당 2), N = 11, `extra_hw_frames=8`.
- **버퍼별 캐시:** fd 번호가 아니라 dma-buf inode(`fstat`의 `st_ino`)를 키로 하며, 디코더 info-change 시 무효화한다. B는 `mmap`을, C는 RGA `importbuffer_fd` 핸들을 캐시한다.
- **RGA 코어:** `im_opt_t.core = IM_SCHEDULER_RGA3_CORE0 | IM_SCHEDULER_RGA3_CORE1`. rkrga debugfs 부하에서 마스크가 지켜지지 않는 것으로 나타나면 `IM_SCHEDULER_RGA3_CORE0` 단독을 쓴다. RGA2는 쓰지 않는다. RGA2와 RGA3는 스케일링 시 샘플링 방식이 달라서, 섞어 쓰면 텐서가 비결정적이 되기 때문이다.
- **색:** RGA와 OpenCV 모두 BT.601 limited range를 쓰며, 스트림에 명시한 limited range(§3)와 맞춘다. 소스의 원래 색 행렬은 기록한다. BT.601과 맞지 않는 부분은 B와 C에 똑같이 나타나며, 타당성 위협으로 보고한다.
- **보간:** RGA의 스케일링 설정을 먼저 고정한다. 그다음 OpenCV는 `INTER_LINEAR`와 `INTER_AREA` 중 C에 대한 §11.1 평균 절대 오차가 더 낮은 쪽을 쓴다. 이 선택은 AMENDMENTS에 기록한다.

## 9. 실행 절차와 유효성

### 9.1 순서

- 매 실행 전에 `tools/collect_env.sh`가 버전, 클럭, 온도, NTP 동기화 상태를 기록한다.
- 각 스윕의 채널 순서는 시드 고정 셔플이다. 정렬된 채널 목록을 Python `random.Random(20261030).shuffle()`로 섞는다. 각 스윕(본편, 보조)은 이 시드로 새 생성기를 쓴다.
- 채널 수마다 6회 실행 전부(B와 C, 3회 반복)가 한 블록을 이룬다. 블록 안에서 반복별 변형 순서는 B→C, C→B, B→C다.
- 한 반복의 두 실행은 세션을 가로질러 나누지 않는다. 둘 사이에서 세션이 끝나면 다음 세션 시작 때 둘 다 다시 실행하며, 이미 끝난 실행은 보존하고 표시한다.

### 9.2 쿨다운 게이트

- 세션을 시작할 때 보드를 10분간 유휴 상태로 둔다. 기준선은 그 유휴 구간의 마지막 60 s 동안의 `soc-thermal` 평균 온도다.
- `soc-thermal` ≤ 기준선 + 3 °C이고 bench 프로세스가 60 s 이상 실행되지 않았을 때만 실행을 시작한다.
- 주변 온도와 냉각 구성은 세션마다 기록한다.

### 9.3 무효 실행

다음 중 하나라도 성립하면 그 실행은 무효다.

1. 창 안의 1초 클럭 샘플(CPU 정책 0/4/6, DDR, NPU) 중 하나라도 고정값(§8)보다 낮다.
2. bench 프로세스가 충돌하거나 비정상 종료한다.
3. 비포화 조건(§6.2)에서 디코더 드롭 > 0. 이 규칙은 H3 실행(§10)에는 적용하지 않는다.
4. 워밍업 시작부터 창의 끝까지 사이에, 송출 서버가 어느 채널에 대해서든 오류, 리더 연결 끊김, 발행자 종료 또는 재시작을 로그에 남긴다. 각 채널의 첫 발행자 시작과 창이 끝난 뒤 bench의 연결 해제는 사건이 아니다. 이 규칙은 H3 실행과 §6.1의 `L` 실행에도 적용한다.

처리:

- 무효 실행은 (쿨다운 게이트를 거친 뒤) 바로 이어서 한 번 다시 실행한다. 재실행이 같은 반복 번호로 그 실행을 대체하며, 무효 실행은 보존하고 표시한다.
- 그 전에 세션이 끝나면(예: 충돌로 재부팅이 필요한 경우), 재실행은 다음 세션 시작 때 그 반복의 다른 실행(§9.1)의 재실행과 함께 수행한다. 이 재실행들이 재실행 역할을 하며 이전의 두 실행을 모두 대체하고, 이전의 두 실행은 보존하고 표시한다.
- 재실행도 무효이면 그 실행은 **무효 2회**로 기록하고 보고한다.
- 운영자는 기록된 외부 장애(전원, 네트워크 링크, 송출 서버)가 있을 때만 실행을 중단한다. 이런 실행은 무효이며, 사유를 보고한다.
- 측정 지점은 유효 실행 3회를 갖추거나, 빠진 실행마다 무효 2회 기록이 있으면 완료된 것이다.
- thermal zone의 `trip_point_0_temp` 이상인 샘플은 무효가 아니라 **경고**로 기록한다.
- 측정 지점에서 가설 지표의 변동계수가 10%를 넘으면 리포트에 표시한다. 재측정을 일으키지는 않는다.
- 유효 여부와 관계없이 모든 원시 실행을 `results/` 아래에 보존한다.

## 10. H3 탐색

본편 조건에서 B와 C 각각에 대해 따로 수행한다. 여기서 드롭된 프레임과 미달한 fps는 무효 사유가 아니라 결과다. §9.3의 1, 2, 4번 규칙은 적용한다.

1. **탐색:** `min(8, L)`채널에서 한 번 실행하고, 실행이 유지되는 동안(HYPOTHESES H3) 실행마다 채널을 1씩 늘린다. 유지하지 못한 첫 실행 또는 `L`에서 멈춘다. 시작 채널 수가 유지되지 않으면 유지되는 실행이 나올 때까지 실행마다 1씩 내려간다. `n`은 탐색 실행이 유지된 가장 큰 채널 수다(하나도 유지되지 않으면 0).
2. **확인:** `n`에서 3회, `n + 1`에서 3회 실행한다. `n = L`이면 `n + 1`에서는 실행하지 않고, `n = 0`이면 `n`에서는 실행하지 않는다.
   - **올림:** `n + 1`에서 3회 중 2회 이상이 유지되면 `n ← n + 1`로 두고 다시 확인한다. 이전의 `n + 1`은 이미 가진 실행과 함께 새 `n`으로 쓴다.
   - **내림:** 그렇지 않고 `n ≥ 1`이며 `n`에서 3회 중 1회 이하가 유지되면 `n ← n − 1`로 두고 다시 확인한다. 이전의 `n`은 이미 가진 실행과 함께 새 `n + 1`로 쓴다.
   - 그 외에는 `n`이 확정된다. H3가 최댓값을 묻기 때문에 "올림"을 먼저 검사한다.
3. 이 절에서 수행한 실행만 센다. 탐색 실행은 확인에 포함하지 않으며, 본편 스윕의 실행은 쓰지 않는다. §9.3의 3번 규칙이 본편 스윕에는 적용되고 여기에는 적용되지 않기 때문이다. 무효 2회인 실행은 유지되지 않은 것으로 세고 표시한다.
4. **순서:** 두 변형이 모두 탐색 중이면 단계마다 번갈아 실행한다(첫 단계는 B→C, 다음 단계는 C→B, 이후 같은 방식). 두 변형이 모두 확인에 필요로 하는 채널 수에서는 6회 실행(변형당 3회)을 B→C, C→B, B→C로 교차하며, 채널 수는 오름차순으로 진행한다. 한 변형만 필요로 하는 채널 수는 그 자리에서 혼자 실행한다. 쿨다운 게이트는 모든 실행에 적용한다.
5. 확정된 `n`이 `n_B` 또는 `n_C`다.

## 11. 동등성과 제로카피 증거

§11.1과 §11.2의 입력: `file_source`의 같은 프레임 1,000개.

### 11.1 텐서 수준 (B 대 C)

- 각 입력 텐서의 640×360 이미지 영역에서 계산한다.
  - 모든 프레임과 원소에 대한 평균 절대 오차 ≤ 2(uint8 스케일).
  - 프레임별 PSNR(피크 255): 모든 프레임에 대한 최솟값 ≥ 35 dB.
- 별도로 검사한다. B와 C의 모든 텐서의 모든 테두리 원소가 114와 같다.

### 11.2 검출 수준 (B 대 C)

다음이 모두 성립하면 `tools/equivalence_check.py`가 통과한다(종료 코드 0).

- 박스는 IoU에 대한 헝가리안 알고리즘으로 클래스별로 짝짓는다. IoU ≥ 0.5일 때만 짝이 성립한다.
- 짝지어진 **모든** 쌍이 IoU ≥ 0.95이고 신뢰도 차이 ≤ 0.02이다.
- **박스 수:** 박스의 신뢰도가 0.25 ± 0.02 범위 안이거나, 신뢰도가 그 범위 안인 박스와 짝지어졌으면 그 박스는 세지 않는다. 모든 클래스에서 B와 C의 센 박스 수가 같으면 그 프레임은 일치한다. 프레임의 99% 이상이 일치해야 한다.

짝지어진 쌍의 IoU와 신뢰도 차이의 히스토그램을 함께 보고한다.

### 11.3 실패

§11.1 또는 §11.2가 실패하면:

- 원인을 분석해 기록한다.
- 이 기준, OpenCV나 RGA 설정, 또는 구현의 변경은 `freeze-m1` 전에 AMENDMENTS에 기록한다.
- 그런 다음 검사를 전체로 다시 실행하며, 리포트에는 최초의 실패를 명시한다.
- §11.1과 §11.2가 그 시점에 유효한 기준으로 통과하기 전에는 §12의 어떤 실행도 시작하지 않는다.

### 11.4 제로카피 증거 (M1-2)

- **perf:** C와 `--variant none`에 대해 1채널과 4채널에서 각각 10 s 동안 `perf record -g`.
  - 호출 스택에 `prepare`, `bind`, `rknn_run`이 포함된 복사 심볼(`memcpy`, `__arch_copy*`)은 전체 샘플의 0.5% 미만이어야 한다. `rknn_run`을 포함하는 것은 런타임 내부에 숨은 CPU 변환을 잡기 위해서다.
  - 이 스택 밖의 복사(MPP, 디먹싱)는 C와 `--variant none` 모두에 있다. 전체 복사 샘플에서 C − none 차이를 보고한다.
- **캐시 유지보수:** `dcache_*_poc`와 `__dma_*sync*` 샘플의 비중을 B와 C 각각에 대해 보고한다. `DISABLE_FLUSH` 플래그를 쓰지 않으므로 런타임이 C의 버퍼에서도 캐시를 유지보수할 수 있으며, 그 비용은 C 쪽에 계상한다.
- **strace**, 정상 상태에서 붙인다. C는 dma-buf `mmap` 호출이 0회이고, B는 프레임당 `DMA_BUF_IOCTL_SYNC` 호출이 정확히 2회다.
- **실패:** 이 절의 기준 중 하나라도 실패하면, 원인을 `freeze-m1` 전에 AMENDMENTS에 기록하고, 모든 C 결과에 그 사실을 표기하며, 리포트에 C의 제로카피 속성이 충족되지 않았음을 명시한다.

## 12. 측정 행렬 (릴리스 `v0.1-m1`)

1. **본편:** B와 C × 본편 집합(§6.1) × 3회 반복, 채널당 5 fps 추론.
2. **보조:** B와 C × 보조 집합(§6.3) × 3회 반복, 채널당 30 fps 추론. H2는 5채널과 H2 보조 지점을 쓴다.
3. **H3:** B와 C의 탐색 및 확인(§10).
4. **A (참조):** A 집합(§6.3) × 3회 반복.

다음은 비교 실행이 아니다.

- 캘리브레이션(M1-3): `L`, `P_cap`, 원시 NPU 한계, 열 확인
- 동등성(M1-4)
- 세션마다 한 번 측정하는 유휴 기준선(§7.2)

**열 확인(M1-3, `freeze-m1` 전):**
- 실행: 가장 큰 보조 채널 수에서의 B와 가장 큰 본편 채널 수에서의 B, 각각 140 s.
- 어떤 클럭 샘플도 고정값 밑으로 내려가지 않고 모든 온도가 `trip_point_0_temp` 아래에 머물면 통과한다.
- 실패하면 냉각 구성을 바꾸고 기록하며, 확인을 반복한다.
- 냉각을 한 번 바꾼 뒤에도 온도가 `trip_point_0_temp`에 도달하지만 어떤 클럭 샘플도 고정값 밑으로 내려가지 않으면, 경고를 기록하고 확인을 수용한다.

## 13. 선택적 M1.1 설계 (어떤 판정에도 쓰지 않음)

M1 결과가 설계를 좌우하지 못하도록 지금 등록한다.

- **B-direct:** B와 같지만, CPU가 캐시되는 dma32 풀에 기록하고, `DMA_BUF_IOCTL_SYNC` END를 호출하며, `rknn_set_io_mem`으로 바인딩한다. 이것은 C의 이득을 "마지막 복사 제거"와 "CPU 변환 제거"로 나눈다. 8채널 본편 + H2 보조 지점, × 3회 반복.
- **K = 4인 B:** 8채널, × 3회 반복. 공유 구조가 B에 불공정한지 확인한다.
- **탐색용, A55 전용:** 파이프라인을 cpu0–3에 고정, 8채널의 B와 C, × 1회. 탐색용으로 표기한다.

`freeze-m1` 이후에 추가한 M1.1 코드는 공유 코어, 디코더, B 또는 C 코드 경로를 바꾸는 경우에만 §15의 적용을 받는다.
