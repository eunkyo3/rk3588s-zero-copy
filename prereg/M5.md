# Pre-registration M5: the packaged path at H1's point

- **Registration:** this file is stage 1 of M5's two stages and gets the tag `prereg-m5`. Its reference time is the `created_at` of the GitHub Release `prereg-m5`. That time is recorded with the tag's commit SHA in the Registration table of `docs/notes/env.md`.
- **Normative text:** this English file. `M5.ko.md` is a translation; if they disagree, this file governs.
- **Changes:** this file is not edited after `prereg-m5`. Later changes, and the values that §8 fixes later, go to [AMENDMENTS.md](AMENDMENTS.md), under the next free number (A16, if none is added first; §9).
- **Base:** [PROTOCOL.md](PROTOCOL.md) v1 applies, with the amendments in force (A1 to A15), except where this file says otherwise. Terms are PROTOCOL's, [M2.md](M2.md)'s and [M3.md](M3.md)'s.
- **Two hypotheses, on process CPU.** M5 asks whether the saving that H1 found for variant C is still there when the path is used as the installed package `rkzc`. Everything else M5 measures is reported without a verdict. M1's, M2's and M3's results are not judged again, whatever M5 finds.

## Disclosure: what was seen before this registration

- **M1, M1.1, M2, M4 and M3:** all of their results. In particular, at H1's point (8 channels, main condition):
  - **M1:** B 43.283 s and C 18.560 s of process CPU, so C is 57.1% lower;
  - **M3,** on the reset board: B 44.433 s and C 19.490 s (+2.66% and +5.01% against M1);
  - **M2,** staggered: C 18.737 s, and 17.600 s with the faster post-processing (Cp), 6.07% lower;
  - **M1.1's A55 design** (one repetition): with every pipeline thread on cpu0–3, C used 51.7 s and B 150.6 s.
- **The package's own checks,** made while it was built ([lib/README.md](../lib/README.md#checked)). They counted frames and compared detections; none measured CPU time or latency:
  - `librkzc` against the registered `tools/demo_detect`: the same detections on 50 frames;
  - 8 channels of looped files for 20 to 30 s, from C++ and from Python: every sampled frame delivered, none dropped;
  - a real RTSP server interrupted in four ways: the channel came back each time;
  - the service installed from the `.deb`, read from its socket by another user, on two channels of looped files.
- **Not seen:** no process CPU, system CPU or latency value of `librkzc`, of `rkzc-detect` or of the service has been measured or looked at.
  - systemd can write the CPU time a service consumed into the journal when it stops. The board's journal of the two-channel tests above holds no such line (counted on 2026-11-20, without displaying any), and `systemctl status` was not read while the service ran.
  - The program does not report its per-frame latency yet (§8 step 2).
- **A fact of the board's configuration,** read on 2026-11-20: systemd's own process is allowed cpu0–7, and no `CPUAffinity` is set for the manager. So a service without the setting is allowed every CPU (§4 rule 5).
- **What was chosen after it:**
  - the threshold of 25%, which is H1's, taken over unchanged (§2);
  - the two configurations of the package (§1);
  - that the comparison is with B and C run in the same sessions, not with M1's numbers.
- **Known before choosing the threshold:**
  - C's saving was 57.1% in M1. With all of its work on A76 cores, the package would have to use about 75% more process CPU than C did to miss 25%.
  - With M1.1's value, if C's work were split between the clusters, the threshold (about 32.5 s) would be crossed at roughly 40% of it on the A55 cores.

  §2 says what this means for the hypotheses.

## 1. What is compared

Four arms at one point, in the same sessions:

| Arm | What runs |
|---|---|
| **B** | `bench_main --variant B`, with M3 §1's options |
| **C** | `bench_main --variant C`, with M3 §1's options |
| **P** | the service `rkzc-detect` of the installed package, as installed |
| **P4** | the same service, restricted to the A76 cores by one line of systemd configuration |

- **The point:** H1's. 8 channels, main condition: 5 inferences per second per channel, 1 frame in 6 of a 30 fps stream, without the staggered sampler. M1's videos and channel assignment over RTSP, the YOLOv8n model (`04a76611…`), 20 s warm-up and a 120 s window, fixed clocks (A7) and cooling (A9).
- **B and C:** the registered code, unchanged. `src/`, `tools/`, `scripts/`, `tests/` and the root `CMakeLists.txt` equal `freeze-m3`'s, built on the board as M3 built them. M5 adds no code to these paths, so M3's reproduction stays runnable from the same commit.
  - `bench_main` accepts no run kind `m5`, so B and C run with `--run-kind check` and M3 §1's other options: `--channels 8 --condition main --warmup 20 --duration 120` and the source `rtsp://10.88.0.1:8554/ch{n}`. Every option that changes what is measured (`--post`, `--stagger`, `--model`, `--prep-threads`, `--cores`) stays at its default. The tool also passes `--out`, with the run's directory under M5's records, and `--repetition`. M5's own record beside each run says what the run is (§8 step 2).
- **The package:** `rkzc` version 0.1.1, or the later version that a change allowed by §8 step 2 makes. What it differs in from the released 0.1.0 is fixed in §8 step 2. It is published as the Release `rkzc-v<version>` before `freeze-m5`, and the board installs that Release's file with `apt install`, as [docs/install.md](../docs/install.md) says, checked against its recorded SHA-256. The model is the one `rkzc-fetch-model yolov8n` fetches.
- **P, "as installed":**
  - the unit file as the package installs it;
  - `/etc/rkzc/detect.toml` as the package installs it, with only the value of `sources` changed, to the eight strings `"rtsp://10.88.0.1:8554/ch1"` to `"rtsp://10.88.0.1:8554/ch8"`, in that order. So `every_nth_frame = 6`, `post = "auto"`, the Unix socket as the output, `empty_frames = true`, `events = true`, and every other key at the shipped value. §3's definitions rely on those two being true: every inferred frame and every source event is a line;
  - **one reader** connected to the socket through the warm-up and the window, which reads every line. It is the measuring tool (§3). A service nobody reads is not the use the package is for.
- **P4:** P with the file `/etc/systemd/system/rkzc-detect.service.d/affinity.conf`, whose two lines are `[Service]` and `CPUAffinity=4-7`. Nothing else differs. This is a setting a user can make without rebuilding anything.
- **What differs between P and C,** all at once. M5 does not separate these:
  - **Post-processing:** the package picks M2's faster one for YOLOv8 (`neon`); C here uses M1's. M2 measured that difference alone, at this point but staggered: 6.07% of C's process CPU.
  - **CPU placement:** `bench_main` pins its pipeline to cpu4–7 and its metrics thread to cpu0. P pins nothing; P4 restricts every thread to cpu4–7.
  - **Start:** `bench_main`'s channels start decoding together once all are open. Each of the service's channels starts when its own source opens, so their arrival phases differ.
  - **What the program does besides:** the package has no timeline and keeps no per-frame records. It maps boxes to the source frame, formats one JSON line per frame and sends it to the socket; it has a monitor thread and reconnection logic. In 0.1.1 it also reads the channel's counters once per frame, inside the callback, for the `decode_errors` field (§8 step 2).
  - **Build and libraries:** `-fPIC`, hidden visibility, and two replaced headers (`lib/shim/`: a failure throws instead of exiting; the cache of decoder buffers can release one channel's entries). FFmpeg's libraries are copied from the build B and C use, stripped and with another run path, so their files differ. `librknnrt.so` is the same file by SHA-256.
  - **How it is run:** as a systemd service under a user made for the run, not as root from a shell.
  - **Who measures:** `bench_main` measures itself; its metrics thread's time, about 0.1 s per window in M3's runs, is inside its process CPU. The service is measured by another process (§3), whose time is outside the service's.

## 2. Hypotheses

Both use PROTOCOL §7.1's process CPU over the 120 s window, as §3 defines it for the service, and the means of the runs that count (§4).

### M5-H1: the package as installed

> At the main condition with 8 channels, the process CPU of the service as installed (P) is at least 25% lower than B's.

- **Spec-literal verdict:** with `B` and `P` the means, *adopted* if `(B − P) / B ≥ 0.25`, otherwise *rejected*.
- **Practical verdict:** the same threshold, except that it is *indeterminate* if, in any run that counts of B or P, some channel's inference rate is below 4.75 fps (§3).
- **Secondary metric:** system CPU from `/proc/schedstat` with the idle baseline subtracted (M2 §3.2). If `(B − P)` has the opposite sign on it than on process CPU, the result is labelled *mixed* in addition to its verdicts. H1's own secondary metric was `/proc/stat`'s; M2 replaced it for the reasons M2 §3.2 gives, and M5 follows M2.

### M5-H2: the package restricted to the A76 cores

> At the main condition with 8 channels, the process CPU of the service restricted to cpu4–7 (P4) is at least 25% lower than B's.

- The verdicts and the secondary metric are M5-H1's, with P4 in place of P.

### Missing runs

- If B, or the arm a hypothesis names, has fewer than 3 runs that count, its spec-literal verdict uses the runs that exist and is flagged, and its practical verdict is *indeterminate*.
- If B or that arm has no run that counts, both verdicts are *indeterminate*.

### What the hypotheses can and cannot tell

- **The threshold is H1's,** taken over unchanged: the question is whether H1's adopted claim also holds for what a user installs. H1's threshold has no recorded rationale (#71), and M5 does not supply one.
- **For P4 it is a lenient test.** With B near 43 s, an arm passes at about 32.5 s or less. C measured 18.6 s. For P4, a rejection would mean the package lost most of the saving; an adoption does not mean it kept all of it.
- **For P, a rejection can also come from the scheduler.** P's threads may run on the A55 cores, where C's path used 51.7 s (M1.1). So M5-H1 tests the package together with where the kernel places it. That is what "as installed" means, and it is why P4 is there.
- **Process CPU in P counts cores of two kinds.** A CPU-second on an A55 core does less work than one on an A76 core. So P's value is not the same quantity as B's, C's and P4's. Where P's work ran is reported (§3).
- **How much of the saving is kept** is in the descriptive values of §6, which have no threshold. They are the more informative part of M5, and they carry the mix of causes listed in §1.
- **Process CPU leaves the reader out,** and favours the service by what `bench_main` spends measuring itself (§1). §6 reports both sizes.
- **The tool shares cpu0 with P,** whose threads may run there too; in B, C and P4 nothing of the pipeline runs on cpu0.
- **One board, one image, one model, one point,** file-backed RTSP streams at 1080p. M5 says nothing about another board, camera, resolution or frame rate.

## 3. Metrics for the service

`bench_main` measures itself. The service is measured from outside, by a tool that runs as root on the board, pinned to cpu0 as `bench_main`'s metrics thread is. The tool is the socket's reader and the sampler in one process. Each definition below is PROTOCOL's, with the difference stated.

- **Frame lines and their order.** Every frame line of 0.1.1 carries its channel, `seq`, `pts_us`, `capture_ns` and `out_ns` (§8 step 2). Within a channel, lines are taken in the order of `seq`, not of arrival: three NPU workers can finish out of order.
- **Start of the service, `t_svc`:** systemd's `ExecMainStartTimestampMonotonic` of the unit, in µs of `CLOCK_MONOTONIC`. Where a UTC time is needed (rule 4), it is `ExecMainStartTimestamp`.
- **Start of the warm-up, `t_start`:** the `CLOCK_MONOTONIC` time at which the tool has read at least one frame line of every channel. `bench_main` starts its warm-up when every source is open, before its first decode; the service's `t_start` is later than that moment by the first frames' way through the pipeline. Both windows begin at least 20 s after every channel runs. The window is `[t_w, t_e)` with `t_w = t_start + 20 s` and `t_e = t_w + 120 s`. The tool reads every line until `t_e` + 2 s, then closes its connection, then stops the service: a frame captured inside the window can arrive after `t_e`.
- **Process CPU (§7.1):** Δ(utime + stime) from `/proc/<MainPID>/stat`, which covers every thread of the process, read at `t_w` and at `t_e`. The actual times of the two reads are recorded; a run whose reads are more than 50 ms from `t_w` or `t_e` is invalid.
- **Where the work ran,** in place of §7.1's split by affinity, which the service's threads do not have:
  - for every thread, Δ(utime + stime) over the window from `/proc/<MainPID>/task/<tid>/stat`, with its name;
  - at each one-second sample, each thread's Δ(utime + stime) since the last sample and the CPU it was last on. The share of P's process CPU on cpu0–3 is the sum of those Δ whose CPU is 0 to 3, over the sum of all;
  - for every arm, system CPU from `/proc/schedstat` per cluster (cpu0–3, cpu4–5, cpu6–7), minus the idle baseline's value for that cluster.
- **System CPU:** M2 §3.2's `/proc/schedstat` sum and PROTOCOL §7.2's `/proc/stat` values, over the same window, minus the session's idle baselines. For P and P4 they include the tool, as they include `bench_main`'s metrics thread for B and C.
- **The tool's own CPU:** Δ(utime + stime) of the tool over the window: the reader and the sampler together.
- **Latency (§7.3):** per frame line, `out_ns − capture_ns`.
  - `capture_ns` is taken when the decoder returns the frame: PROTOCOL's `t0`.
  - `out_ns` is taken in the frame callback, before the counters are read and the line is formatted. It is later than PROTOCOL's `t4` by the mapping of the boxes to the source frame and by the wait for the callback lock.
  - p50 and p99 are over the lines of all channels with `out_ns` inside the window, by `numpy.percentile` with its default.
  - The other stage times of §7.3 are not available for the service.
- **Arrival phases:** each channel's `capture_ns` modulo 200 ms over the window, as M2 §3.1 describes them for `t0`.
- **Inference rate (§7.4):** per channel, the lines with `out_ns` inside the window, divided by 120 s.
- **Drop rate (§7.5):** the program numbers a channel's frames in decode order (`seq`), never starting again, and samples those with `seq` divisible by 6. For each channel, take its lines with `capture_ns` inside the window. The sampled frames expected are the multiples of 6 from the smallest to the largest `seq` among them; those without a line were dropped or failed. The rate is their number over the expected number, all channels together. The service's own counters at its stop (`dropped`, `errors`) are reported next to it.
- **Decoder drops (§7.6):** per channel, over its lines with `pts_us` ≥ 0, from the last such line with `out_ns` before `t_w` to the last with `out_ns` before `t_e`:
  - a step with Δpts ≤ 0 counts 1;
  - any other step counts `max(0, round(Δpts / period) − Δseq)`, with the period of 1/30 s. `seq` advances only for a frame the decoder returned, so a frame it never returned shows as a step of `pts_us` larger than that of `seq`;
  - the channel's decode errors over the same span: every frame line carries the channel's count so far (`decode_errors`, §8 step 2), and the difference between those two lines is added;
  - a channel with no line of `pts_us` ≥ 0 in the window counts 1.

  §7.6 also counts frames flagged as corrupt, which the program does not hand out; the decode errors are the program's own count of the decoder's error returns.
- **Receive drift (§7.6):** per channel, between its first and its last line in the window: `D = (30 × Δt0 − Δseq) / 30` seconds, with `Δt0` the difference of their `capture_ns` in seconds. It is an end value, given once per run; it is not `bench_main`'s maximum over the one-second samples, and the two are not compared.
- **One-second samples (§7.7):** by the tool: NPU load per core, every thermal zone, the clocks of CPU policies 0, 4 and 6, DDR and NPU, the service's VmRSS, and each thread's CPU time and last CPU.

## 4. Runs, order and validity

- **Runs:** 4 arms × 3 repetitions = 12, in one sweep.
- **Order within a repetition:**
  1. B, C, P, P4
  2. P4, P, C, B
  3. C, B, P4, P

  The four runs of a repetition are never split across sessions. If a session ends inside a repetition, the whole repetition is rerun at the start of the next session, in the same order; the runs already finished are kept and flagged.
- **Sessions:** as M3 §3: 10 minutes idle with the soc-thermal and both system CPU baselines, the cooldown gate (PROTOCOL §9.2) before every run, and the environment recorded before every run (§9.1). The operator reports the ambient temperature at each session's start.
  - **For the gate, the service is a bench process:** no `bench_main` and no `rkzc-detect` process has run for at least 60 s, and the tool checks that none exists before every run.
  - **A session ends** by a reboot, a cooling change or 30 minutes without a run. The operator ends one only between repetitions, or for a logged external failure (power, network link, stream server). Any other end inside a repetition is reported with its reason.
- **The package during the session:** installed before the session's idle period, with the service stopped and disabled. The service runs only during P's and P4's runs. P4's drop-in is in place only for P4's runs, and systemd reloads its configuration after every change of it.
- **Inventory:** before a session starts, M3 §4's pinned keys must equal `docs/notes/inventory_m1.txt`. Installing the package adds files under `/opt/rkzc`, `/usr`, `/etc/rkzc` and `/var/lib/rkzc` and changes none of those keys: `bench_main` does not load the package's libraries. The package's SHA-256, and those of the libraries in `/opt/rkzc/lib`, are recorded per session.
- **Validity of B's and C's runs:** PROTOCOL §9.3, rules 1 to 4, as in M3 §3.
- **Validity of P's and P4's runs:** the same four rules, read for the service. A run is invalid if any of these holds:
  1. any one-second clock sample in the window is below its fixed value;
  2. between `t_svc` and `t_e`: the service's main process exits, or systemd restarts it; or some channel has no frame line by `t_svc` + 60 s; or the service closes the tool's connection before the tool does; or its journal holds a `frame_error` event. Also, whenever it happened: the service's stop log counts a client disconnected for not reading, or one refused as too many. Also: a process CPU read is late (§3), or the tool does not complete the run (its crash, a lost link to the stream PC);
  3. decoder drops (§3) > 0; or, between `t_svc` and `t_e`, the service's journal holds a source event other than each channel's first `source_opened`;
  4. the stream server's log, as rule 4 says, from `t_svc` to `t_e`. The reader's connection to the socket is the tool's, not the stream server's;
  5. **the arm is not the arm:** at `t_w` or at `t_e`, some thread of a P run is not allowed every CPU of 0 to 7, or some thread of a P4 run is allowed a CPU outside 4 to 7.

  `bench_main` ends on a frame that fails, which is rule 2 for B and C; the service skips such a frame, so rule 2 names the event.
- **Handling:** an invalid run is repeated once, right after it, after the cooldown gate. If the repeat is invalid too, the run is invalid ×2 and counts as missing. Attempts count across sessions as `docs/notes/comparison.md` says: a run whose earlier attempt was invalid gets only its one repeat. The CV flag of §9.3 applies to process CPU.
- **The runs that count:** per repetition and arm, the valid run of the session that completed the repetition.

## 5. What could go wrong, and what then

- **The package does not install, or the service does not start at 8 channels, in the checks before `freeze-m5`:** the fix changes only what failed, and an amendment gives its diff and a new version and SHA-256 (§8 step 2). After `freeze-m5`, a service that does not start is an invalid run (§4 rule 2).
- **P drops frames or runs below 4.75 fps:** its runs stay valid if §4's rules hold. The practical verdict of M5-H1 is then *indeterminate* (§2), and the drop rate is reported. Nothing is tuned.
- **P's threads move between core clusters from run to run:** that is P, as installed. The spread is reported; the CV flag may be set.
- **Every run of an arm is invalid by the same rule:** the arm has no run that counts, and its hypothesis is *indeterminate*. The rule is not relaxed.
- **A defect:** a value or a rule computed otherwise than this text says, in the tool or the package. It is fixed by an amendment, and the sweep is rerun whole. The report says when each defect was found and whether results had been looked at by then. Superseded runs stay under their records and are reported. A run that merely failed is not a defect but an invalid run.
- **Not changed, whatever any run shows, the checks of §8 step 3 included:**
  - §2's threshold and verdict rules;
  - the point, the arms and their configuration (§1);
  - §4's number of runs (3 repetitions of each arm), its order, session, validity and handling rules, and the runs that count;
  - §3's metric definitions and §6's headline values;
  - the package and the tool once they are fixed (§8 step 2), except as that step allows.

## 6. Reporting

- **The hypotheses:** each with its two verdicts, its relative difference `(B − arm) / B`, the secondary metric's sign, and §2's notes.
- **The headline values, with no threshold,** for P and for P4, from the means of the runs that count:
  - `(arm − C) / C`: how much more process CPU than C;
  - `(B − arm) / (B − C)`: the share of C's saving that the arm keeps.
- **Descriptively, with no threshold:**
  - for each metric, the paired differences `P_r − C_r`, `P4_r − C_r` and `P4_r − P_r` over the repetitions that have both runs, their means, and a descriptive 95% t interval (degrees of freedom: pairs − 1; none with fewer than 2 pairs); for process and system CPU also the mean of `(arm_r − C_r) / C_r`;
  - process CPU, both system CPU measures with the per-cluster split, latency p50 and p99, arrival phases, inference rate, drop rate, the highest temperature, VmRSS;
  - where P's work ran, and the tool's own CPU;
  - B's and C's process CPU without their metrics thread's time (`process_cpu_s − process_cpu_a55_s` of `bench_main`'s summary: the thread pinned to cpu0), next to the values with it;
  - B and C next to M1's and M3's values at this point;
  - the values of every run, valid or not.
- **Said with them:** that the differences from C mix the causes of §1, and that latency in an unstaggered run depends on arrival phases that are not controlled (M3 §2) and that differ in kind between `bench_main` and the service (§1).
- **Release:** a report `docs/report/M5.md` with its tables, under its own tag. [docs/install.md](../docs/install.md) and [lib/README.md](../lib/README.md) then say what was measured instead of "not measured".

## 7. What M5 does not tell

- **Why P differs from C:** the causes of §1 are not separated. `bench_main` can run the package's post-processing unstaggered (`--post neon`) without a code change, and M5 does not use that; an unpinned `bench_main` would need a change to the registered code.
- **The cost of other uses of the library:** a Python callback, several readers, stdout as the output.
- **Reconnection under load, long runs, memory growth:** the window is 120 s on streams that do not fail.
- **Anything about B:** B is not packaged. It is here as the reference H1 used.

   - **Detections:** the service's lines against `rkzc-jsonl`'s, with one file as the only source of each, as the package's own tests compare them: the same detections.
   - **Affinity:** in one run of P4, every thread of the service is allowed cpu4–7 only; in one run of P, cpu0–7.
   - **One run of each arm** at the point, with windows of 10 s. Their CPU and latency values are reported in the amendment of step 4. Nothing that this file fixes changes because of them (§5).
4. **`freeze-m5`:** it tags the commit whose AMENDMENTS holds the values below. Its Release `created_at` is the reference time for M5's runs.

## 9. Amendments

- **Numbering:** M5's amendments go to AMENDMENTS.md under the next free numbers. The latest is A15; M3 may still add its own.
- **PROTOCOL §15 applies** with `freeze-m5` in place of `freeze-m1`:
  - Before `freeze-m5`, measurements affected by a change are redone from scratch.
  - After it, a change to any of the following invalidates every M5 run that used it: the package (the library, the program, the unit file, the shipped configuration), the tool, or the registered code B and C run.
  - The sweep is then rerun whole, for all four arms.
  - Superseded runs stay under their records and are reported.
- **Releases:** every amendment made after `prereg-m5` is published as its own Release `amend-A<n>`.
