## 1. What is compared

Two sweeps, each in a session of its own:

| Sweep | Point | Arms |
|---|---|---|
| `m7_main` | H1's: 8 channels, main condition (5 inferences per second per channel) | B, Bd, Rc, C, Bk, Bdk, Rck, Ck |
| `m7_aux` | 5 channels, auxiliary condition (30 inferences per second per channel) | B, Bd, Rc, C, Ct, Cpt |

| Arm | What runs | New code |
|---|---|---|
| **B, Bd, Rc, C** | M6's four cells (M6 §1), with the snapshots of this section | an option |
| **Bk, Bdk, Rck, Ck** | the same four, snapshots included, with the PMU's counters on every pipeline thread | an option |
| **Ct** | C with the thread CPU time of every `rknn_run` recorded (M6 §1), with the snapshots | an option |
| **Cpt** | Ct with the package's post-processing: `--variant C --post neon --time-rknn on`, with the snapshots | an option |

- **Both points** use M1's videos and channel assignment over RTSP, the YOLOv8n model (`04a76611…`), 20 s warm-up and a 120 s window, fixed clocks (A7) and cooling (A9), without the staggered sampler. The auxiliary point is M1.1's `bdirect_aux` point.
- **Four questions, each with its arms:**
  1. **Conversion or copy at the auxiliary condition (#62).** B, Bd, Rc and C in `m7_aux`: M6's four cells, at the point M6 did not run.
  2. **The decoder's threads.** B, Bd, Rc and C in `m7_main`, and the same four with counters. Whether C's decoder threads again use more CPU than Bd's (M7-H2), and whether a difference comes with more instructions or with slower ones (a description).
  3. **The kernel's side (#59).** Every arm of both sweeps records what else ran on the board during its window.
  4. **`rknn_run` at the auxiliary condition (#60).** Ct and Cpt in `m7_aux`, and a probe of the output bindings outside the pipeline (§3).
- **The four cells are bundles,** as M6 §1 says: they differ in slot memory and cache syncs as well as in "conversion" and "copy". Nothing in M7 changes that.

### The new options

- **`--snapshot on`** (every arm of M7). At two moments the metrics thread, on cpu0, reads:
  - for every thread of every process of the system that is not `bench_main` (each `/proc/<pid>/task/<tid>`): its ids, its name, whether it is a kernel thread (its process's parent is pid 2, or it is pid 2), and its run time from its `schedstat`;
  - `/proc/interrupts`, `/proc/softirqs`, `/proc/stat` and `/proc/schedstat`, whole;
  - for every thread of `bench_main`: its run time, its time waiting to run and its number of timeslices from `/proc/<pid>/task/<tid>/schedstat`, and its voluntary and involuntary context switches from its `status`.

  And between the two moments one counter of `cpu_cycles` counts on cpu0, for every task and the kernel (a CPU's counter, not a thread's).
  - **The two moments:** the first is at the metrics thread's tick one second before the window's start, after that tick's sample; the second is right after the window's end values are read. So the snapshots' span is the window and about one second before it: 121 s and the time the last reads take. Nothing is read inside the window, and the window's own start and end values are read when they were without the option. To keep it so, the first snapshot stops reading 50 ms before the window's start if it has not finished; it is then incomplete and counts as missing (§4).
  - **Not rescaled:** the snapshots' values are reported over their own span, whose length the files give, except in the two places that say they scale (M7-H2's "Mixed", and the idle pair of §4). The span is made the same way in every arm.
  - **A thread that is in one snapshot only:** if only in the second, it started inside the span, and its run time counts. If only in the first, it ended inside the span; it is counted and listed, and what it ran after the first moment is not known. A thread that ends while it is being read is such a thread, not a failed read.
  - **The run's other values do not change:** `frames.csv`, `summary.csv` and `threads.csv` are as without the option. The snapshots go to files of their own.
  - **One implementation:** the idle pair of §4 is read by a small tool built from the same source file.
- **`--thread-counters on`** (Bk, Bdk, Rck, Ck). For every pipeline thread that exists when the warm-up ends, one group of five counters of `armv8_pmuv3`, counting in user and kernel mode, on that thread wherever it runs: `cpu_cycles`, `inst_retired`, `l2d_cache_refill`, `l3d_cache_refill` and `stall_backend`.
  - The groups are opened before the window and are enabled at its start and disabled at its end, each by one call per thread from the metrics thread. Each group's `time_enabled` and `time_running` are read with its values, and the thread's run time from its `schedstat` is read when its group is enabled and when it is disabled.
  - **Why separate arms:** a thread's counters are saved and restored at each of its context switches. How much CPU that costs here is not known, so B, Bd, Rc and C stay without them, and `Xk − X` is reported for each cell.
  - **An event is left out** only if it cannot be opened on this kernel, or if it counts zero on every thread of the decoder's group in the check of §8 step 3. The amendment of §8 says so, and the group has the events that remain. The set is fixed before `freeze-m7`. `cpu_cycles` and `inst_retired` are needed: without either, the four counted arms are not run.
- **Unchanged arms stay unchanged.** With both options at their defaults, every arm of M6 does what the code of `freeze-m6` does with the same options. §8 step 2 says which files may change, and step 3 checks it for the arms M7 runs. By and Cpf, which M7 does not run, have the object hashes of step 2 only.

## 2. Hypotheses

Both use the means of the runs that count (§4). Each has a spec-literal and a practical verdict, as H1 had. Each threshold comes with its reason, and with the decision rule's approximate error rates. The error rates assume independent runs and normal errors, and ignore that the spread differs between sessions.

### M7-H1: the conversion carries the saving at the auxiliary condition too

> At the auxiliary condition with 5 channels, moving the conversion to RGA3 while the CPU still copies into the NPU's input (Rc) gives at least 90% of C's saving against B.

- **Metric:** PROTOCOL §7.1's process CPU over the 120 s window, in `m7_aux`.
- **Spec-literal verdict:** with `B`, `Rc` and `C` the means, *adopted* if `(B − Rc) / (B − C) ≥ 0.90`, otherwise *rejected*.
- **The threshold's reason:** it is M6-H1's, at the second point #62 named. Two earlier results give different expectations:
  - M1.1's Bd saved about 1% of `B − C` here. If Rc's bundle costs what B's copy bundle did, the ratio is about 0.99.
  - M6's `Rc − C` was 1.60 s over 4,800 inferences, 0.33 ms per inference. If that holds per inference, it is 6.0 s over 18,000 inferences, 6.4% of M1.1's `B − C` of 93.5 s, and the ratio is about 0.94.

  A result below 0.90 would mean that Rc's bundle costs more per inference at 30 fps than it did at H1's point.
- **Error rates, approximate:** with M1.1's sd of 0.56 s (B) and 1.41 s (C, taken for Rc as well), the standard error of the ratio is about 1.2 points. The rule then adopts with a probability above 99.9% if the true share is 95%, and below 0.1% if it is 85%. At 90% either verdict is about as likely as the other. At the lower expectation, 0.94, the threshold is about three standard errors away.
- **Mixed:** if the same ratio from `/proc/schedstat` (M2 §3.2) is on the other side of 0.90.

### M7-H2: C's decoder threads use more CPU than Bd's

> At the main condition with 8 channels, the decoder's threads of C use at least 0.50 s more CPU per 120 s window than those of Bd.

- **Metric:** the CPU time over the window of the decoder's thread group, from `threads.csv`: the threads `dec-*`, `mpp_dec_parser` and `mpp_dec_hal`, as [cpu_breakdown.md](../docs/notes/cpu_breakdown.md) groups them. `D(arm)` is its mean over the runs that count, in `m7_main`, of the arms without counters.
- **Spec-literal verdict:** *adopted* if `D(C) − D(Bd) ≥ 0.50 s`, otherwise *rejected*.
- **The threshold's reason:** the difference was seen after the fact, in two sessions: 1.04 s (M1.1) and 1.14 s (M6). 0.50 s is about half of either and the lower end of M6's interval. This hypothesis asks whether the difference appears a third time when it is named beforehand.
- **Error rates, approximate:** with M1.1's sd of the group (0.42 s for Bd, 0.16 s for C), the standard error of the difference of two means is about 0.26 s. The rule then adopts with a probability of about 99% if the true difference is 1.1 s, and of about 3% if it is 0. So if the difference is what the two sessions showed, an adoption is the expected result.
- **Mixed:** if the same difference from the snapshots' run times of those threads (§1), scaled from the snapshots' span to 120 s, is on the other side of 0.50 s. If any run that counts of Bd or C has no snapshots, there is no label, and the report says so.
- **What an adoption says:** that on this board C's decoder threads use more CPU than Bd's, in three sessions. It does not say why; question 2's counters describe it (§6).
- **What a rejection says:** that the difference of M1.1 and M6 did not repeat at this size. The earlier values stand as they were reported.

### For both

- **Practical verdict:** the spec-literal one, except that it is *indeterminate* in either of these cases:
  - in any run that counts of an arm the hypothesis names, some channel's inference rate (PROTOCOL §7.4) is below 4.75 fps at the main condition, as [HYPOTHESES.md](HYPOTHESES.md)'s H1 has it, or below 28.5 fps at the auxiliary condition, as M2 §2 has it;
  - the mean drop rates (PROTOCOL §7.5) of two arms the hypothesis names differ by more than 1 percentage point.
- **Missing runs:** if an arm a hypothesis names has fewer than 3 runs that count, its spec-literal verdict uses the runs that exist and is flagged, and its practical verdict is *indeterminate*. With no run that counts, both are *indeterminate*.
- **A threshold met exactly counts as met** (A17's reading).

### What the hypotheses can and cannot tell

- **M7-H1 is the expected result,** as M6-H1 was. It tests the one cell the auxiliary condition has never had, and compares bundles, not a pure "copy".
- **M7-H2 is about a difference of about one second** between thread groups whose sd over three runs has been between 0.09 and 0.75 s. Three runs can show a difference of that size and cannot bound it closely.
- **Neither says anything about M6-H1.** `m7_main` runs B, Rc and C again, and their ratio is reported next to M6's without a verdict (§6).
- **One board, one image, one model, two points,** file-backed RTSP streams at 1080p.

## 3. Metrics

- **All arms are `bench_main`:** PROTOCOL §7's metrics, as M3 §1 and M2 §3.2 (`/proc/schedstat`) have them.
- **From the snapshots,** per run, as the difference between the two moments:
  - **Kernel threads' CPU:** the sum of the run time of all kernel threads, and the same by name group: `mpp_worker_*`, `irq/*-rga3`, names holding `rknpu` or `npu`, `kworker/*`, `ksoftirqd/*`, and the rest.
  - **Other processes' CPU:** the sum for all other tasks that are not kernel threads, and the five largest by name.
  - **Threads that are in one snapshot only** are counted and listed, as §1 says.
  - **Interrupts:** the count per line of `/proc/interrupts` whose name holds `npu`, `rga` or `rkvdec`, per CPU, and the total of all lines.
  - **Soft interrupts:** `/proc/softirqs`' counts per kind.
  - **`/proc/stat`:** its `irq` and `softirq` columns, as the kernel gives them.
  - **cpu0's busy time by its counter:** the cycles divided by cpu0's fixed clock, 1800 MHz (A7), and next to it cpu0's own value from `/proc/schedstat` over the same span. The counter is read right after the second moment's `/proc/schedstat`. Their difference is the time cpu0 was active outside every task: interrupts handled while it was idle, and what entering and leaving idle costs. It also holds the metrics thread's last slice, which `/proc/schedstat` adds only when the thread is switched out: the reads at the window's end and the second snapshot's. The files give those reads' duration, and the report gives the difference with it and without it. The counter's value and these differences are reported only if §8 step 3's check of the counter passed; otherwise the report says that it failed and gives no value.
  - **Per thread of `bench_main`,** by thread group: timeslices, voluntary and involuntary context switches, and time waiting to run.
- **From the counters (the counted arms),** per thread group, over the window: each event's count, instructions per cycle, and cycles divided by the A76's fixed clock (2208 MHz) next to the group's run time read with the counters (§1), and their ratio as the clock the counters saw.
- **For Ct and Cpt:** M6 §3's values: the sum of the NPU workers' thread CPU across `rknn_run`, its share of process CPU, the mean per call, the mean wall time of the same stage, and the number of calls.
- **Latency** is PROTOCOL §7.3's for every arm, described and not judged: arrival phases are not controlled.

### The probe of the output bindings (#60)

Outside the pipeline, as `tools/output_probe` measured the output path's options before M2: one context on NPU core 0, the YOLOv8n model, a cached input from `rknn_create_mem` written by the CPU, two frames of video ①.

- **Configurations,** each with a context of its own, its outputs bound with `rknn_set_io_mem`:
  1. NCHW, INT8: the pipeline's binding, and the reference;
  2. NHWC, INT8;
  3. NCHW, FLOAT32;
  4. NHWC, FLOAT32;
  5. the attributes `RKNN_QUERY_NATIVE_OUTPUT_ATTR` gives, unchanged;
  6. the attributes `RKNN_QUERY_NATIVE_NHWC_OUTPUT_ATTR` gives, unchanged.
- **Accepted or refused:** a configuration is *refused* if a query, `rknn_set_io_mem` or `rknn_run` returns an error, or if its outputs in 40 runs alternating the two frames do not all equal configuration 1's, compared after the conversion its layout and type call for (INT8 values must be equal; a permutation of the axes; for NC1HWC2, the channels put back in NCHW order with the padding channels dropped; for FLOAT32, `(q − zero point) × scale`, with a difference of at most half of that output's scale, so that a runtime that converts in half precision is not refused for it). A refused configuration is reported with its reason and has no cost.
- **Each configuration runs in processes of its own,** so that one that crashes is refused and the others still run: one process for the 40 runs above, and one per round for the cost.
- **Cost,** for each accepted configuration: over 15 rounds, in each of which every accepted configuration's process is started once, in an order that rotates by round, and makes 20 timed runs: the thread CPU of the calling thread across `rknn_run` (`CLOCK_THREAD_CPUTIME_ID`) and the process CPU across it, per run; the median and the range over the rounds, and the difference from configuration 1.
- **What it is:** a description of one context that runs alone. It is not the pipeline, and no hypothesis rests on it.

## 4. Runs, order and validity

- **Runs:** `m7_main` 8 arms × 3 repetitions = 24; `m7_aux` 6 arms × 3 repetitions = 18. The probe of §3 once, after `m7_aux`'s last run, in the same session.
- **Order within a repetition:**
  - `m7_main`:
    1. B, Bd, Rc, C, Bk, Bdk, Rck, Ck
    2. Ck, Rck, Bdk, Bk, C, Rc, Bd, B
    3. Bdk, Bd, C, Ck, Rc, Rck, B, Bk
  - `m7_aux`:
    1. B, Bd, Rc, C, Ct, Cpt
    2. Cpt, Ct, C, Rc, Bd, B
    3. Rc, C, B, Bd, Cpt, Ct
  - **How it was chosen,** before any run: in each sweep the second order is the first reversed, so that over these two every arm has the same mean position. The third keeps the arms of the sweep's hypothesis next to each other (Bd and C; Rc, C and B) and, in `m7_main`, each counted arm next to its cell. Three orders cannot balance the arms; the report gives every run's position, and the paired differences are within repetitions.
  - **An arm that is not run** (§5) is left out, and the order of the others stands.
  - The runs of a repetition are never split across sessions. If a session ends inside a repetition, the whole repetition is rerun at the start of the next session, in the same order; the runs already finished are kept and flagged.
- **Sessions:** as M6 §4 and M3 §3: 10 minutes idle with the soc-thermal and both system CPU baselines, the cooldown gate (PROTOCOL §9.2) before every run, and the environment recorded before every run (§9.1). The operator reports the ambient temperature at each session's start. `m7_main` is run first. A session of `m7_main` takes about 1 hour 35 minutes, and one of `m7_aux` about 1 hour 20 minutes.
  - **A session ends** as M6 §4 says: by a reboot, a cooling change or 30 minutes without a run; the operator ends one only between repetitions, or for a logged external failure.
  - **During the idle baseline** one pair of snapshots is taken 121 s apart by `tools/`, with the same reads as `--snapshot on` and without the counter, so that the report has what the idle board does in a span like a run's. Where the report subtracts it, the idle pair's values are scaled to the run's span.
- **Inventory:** before a session starts, M3 §4's pinned keys must equal `docs/notes/inventory_m1.txt`.
- **Validity:** PROTOCOL §9.3, rules 1 to 4, as in M3 §3, for every arm. In addition:
  - **Rule 5, the counted arms:** the run is invalid if some pipeline thread in `threads.csv` (the window's end) has no group of counters, or if for some group `time_running` differs from `time_enabled`.
  - **Snapshots do not decide validity.** If a snapshot file of a run is missing, incomplete (§1) or cannot be parsed, the run stays valid, its snapshot values are missing, and the report lists it.
- **Handling:** an invalid run is repeated once, right after it, after the cooldown gate. If the repeat is invalid too, the run is invalid ×2 and counts as missing. Attempts count across sessions as `docs/notes/comparison.md` says. The CV flag of §9.3 applies to the process CPU of B, Rc and C in `m7_aux` and to the decoder group's CPU of Bd and C in `m7_main`: above 10%.
- **The runs that count:** per repetition and arm, the valid run of the session that completed the repetition.

## 5. What could go wrong, and what then

- **A counter cannot be opened, or the check of the counters fails** (§8 step 3): §1 says which events are left out, and for no other reason. If the check fails with the events that remain, in any of its three parts, Bk, Bdk, Rck and Ck are not run; question 2's description by counters is then missing, and M7-H2 is not affected.
- **The check of the snapshots fails:** the option has a defect, and `freeze-m7` waits for its fix.
- **Cpt's check fails:** Cpt is not run, and question 4 has Ct alone.
- **cpu0's counter fails its check:** its value is not reported (§3). Nothing else changes.
- **The counters cost much:** the counted arms are run as registered, and `Xk − X` says how much. If the mean of `Xk − X` is above 2% of `X`'s process CPU in some cell, the report says for that cell that the counted arm is not the cell with counters added but an arm of its own, and reads question 2's counters with that said.
- **A snapshot takes long:** the report gives its duration. It is outside the window (§1). The check of §8 step 3 shows that the first is finished before the window's start. In a run in which it is not, it stops early (§1), the window is not touched, and the run's snapshot values are missing.
- **Rc at the auxiliary condition drops frames or runs below 28.5 fps:** its runs stay valid if §4's rules hold. §2 says when M7-H1's practical verdict is then *indeterminate*. Nothing is tuned.
- **The probe:** a configuration that is refused, or whose process crashes, is a result (§3). If configuration 1 itself fails, the probe has a defect; it is fixed by an amendment and the probe alone is rerun, since no sweep's run uses it.
- **Every run of an arm is invalid by the same rule:** the arm has no run that counts, and a hypothesis that names it is *indeterminate*. The rule is not relaxed.
- **An unchanged arm is changed:** if a check of §8 step 3 finds that an arm of M6 no longer does what `freeze-m6`'s code does, the new code has a defect, and `freeze-m7` waits for its fix.
- **A defect after `freeze-m7`:** a value or a rule computed otherwise than this text says. It is fixed by an amendment, and the sweep it affects is rerun whole; a defect in what both sweeps use reruns both. ## 7. What M7 does not tell

- **Time in hard interrupt handlers, as a value of its own:** `/proc/stat`'s `irq` column read 0, and M7 installs no tracing tool. Inside a task's time it is not separated; in idle time it is bounded loosely, on cpu0 only, by one counter.
- **Why, in a causal sense, the decoder's threads differ:** the counters say whether more instructions ran or the same ran slower. They do not say which code, and M7 changes nothing to test a cause.
- **A pure cost of "the copy":** each cell is a bundle (M6 §1).
- **What `rknn_run` does with its CPU time in the pipeline:** the probe compares bindings for one context that runs alone.
- **Counters at the auxiliary condition:** the counted arms run at H1's point only.
- **Power and memory traffic** ([#58](https://github.com/eunkyo3/rk3588s-zero-copy/issues/58)), **other points, models, boards or software.**
