# Pre-registration M3: one-command reproduction on a reset board

- **Registration:** this file and amendment A15 are registered together, in one stage. The tags `prereg-m3`, `amend-A15` and `freeze-m3` all mark the commit that adds them. The reference time is the `created_at` of the Release `freeze-m3`, recorded with the tag's commit SHA in the Registration table of `docs/notes/env.md`.
- **Normative text:** this English file. `M3.ko.md` is a translation; if they disagree, this file governs.
- **Changes:** this file is not edited after `prereg-m3`. Later changes go to [AMENDMENTS.md](AMENDMENTS.md), numbered on from A15 (§9).
- **Base:** [PROTOCOL.md](PROTOCOL.md) v1 applies, with the amendments in force (A1 to A15), except where this file says otherwise. Terms are PROTOCOL's.
- **One criterion, no hypothesis test.** M3 asks whether the scripts in this repository, run on a reset board, give M1's values at H1's point within ±10%. That criterion comes from the project's plan (§2). M1's verdicts are not judged again, whatever M3 finds.

## 1. What is reproduced

- **The point:** H1's, in M1's conditions:
  - variants B and C;
  - 8 channels, main condition: 5 inferences per second per channel, 1 frame in 6 of a 30 fps stream, without the staggered sampler;
  - every other option at `bench_main`'s default: M1's post-processing, the YOLOv8n model, K = 2 preprocessing threads, the A76 cores;
  - 20 s warm-up and a 120 s window, M1's videos and assignment over RTSP, fixed clocks (A7) and cooling (A9).
- **The metrics:** process CPU (PROTOCOL §7.1) and p50 latency (§7.3), each as the mean over a variant's runs that count (§3).
- **M1's values** (sweep `main`, `results/comparison/20261103T073439Z_main`, 3 runs per variant at 8 channels; [M1_tables.md](../docs/report/M1_tables.md)):

  | | B | C |
  |---|---|---|
  | Process CPU | 43.283 ± 0.343 s | 18.560 ± 0.308 s |
  | p50 latency | 33.117 ± 4.543 ms | 30.340 ± 0.961 ms |

## 2. The criterion

- **Within ±10%:** for each variant and each metric, |(M3 − M1) / M1| ≤ 0.10. M3 is the mean of the `m3_after` runs that count, and M1 the value of §1. Both are unrounded.
- **The outcome** is one of three:
  - **reproduced:** all four hold;
  - **not reproduced:** at least one does not hold;
  - **not determined:** a variant has no run that counts, and none of the others fails.
- **Each of the four** is reported with its relative difference, whatever the outcome.

### What the criterion can and cannot tell

- **B's p50 latency is a weak test.** It varied across M1's three runs (sd 4.543 ms, 13.7% of its mean), because the channels' arrival phases are not controlled at this point (M2 §3.1).
  - The runs here are unstaggered too, to match M1.
  - Suppose nothing changed, and the new runs vary as M1's did. Take M1's sd as the true one, and a normal model. Then the difference between two means of 3 runs has an sd of 3.709 ms. Against a bound of 3.312 ms, the mean of 3 new runs would be outside ±10% with probability about 37%.
  - That figure is rough:
    - with the sd estimated from 3 runs (a t distribution with 2 degrees of freedom), it is about 47%;
    - M1's three values, 35.3, 36.1 and 27.9 ms, look like two clusters rather than a normal spread.
  - Under the same model, the probability is about 0.01% for C's p50, and below 0.1% for both CPU values. With the t distribution, these become about 6%, 0.4% (B) and 1.8% (C).
  - So a miss on B's p50 alone says little. It is reported as such, and the outcome is still "not reproduced".
- **It tests the chain as a whole:**
  - the reset;
  - the scripts;
  - the code since M1's binary (§4);
  - the packages at install time;
  - two weeks' time.

  The `m3_before` runs separate the reset and setup from the rest. They are compared descriptively, not judged (§6).
- **It is the same board,** not another unit or another RK3588 board (#70), and the same stream PC, which is not reset.

## 3. Runs and their order

1. **`m3_before`:** one sweep on the board as it is, before its reset, by `scripts/reproduce_m1.sh before`. Its records are copied off the board before the reset, which wipes them.
2. **The reset:** FriendlyElec's factory reset. `firstboot` marks the data partition, and the next boot wipes it, which returns the root file system to the image as flashed. The operator then gives the board a network link again, by hand.
3. **The setup:** `scripts/setup_board.sh`, on the reset board, from a clone of this repository.
   - **The clone's commit:** it must have `freeze-m3`'s row in `docs/notes/env.md`, which comes in a commit after the tag, as for M2 and M4. Its code (`src/`, `tools/`, `scripts/`, `tests/`, `CMakeLists.txt`) must equal `freeze-m3`'s. Both scripts check this.
   - It records itself in `results/m3/<UTC>_setup/`.
   - Its record says the board was **fresh**: none of the files that a set-up board has and the image does not (A15) was there when it started. Before its first change, it writes one of them itself, so that a second attempt on the same board is not fresh.
   - It also records the image's `rom-version`, the boot time and the first line of the package log, all read before its first change.
4. **`m3_after`:** one sweep on the reset board, by `scripts/reproduce_m1.sh after`.

- **Each sweep:** 3 repetitions, in PROTOCOL §9.1's variant order B→C, C→B, B→C. It runs as a protocol session of `tools/stream_session.py`, with:
  - 10 minutes idle, with the soc-thermal and system CPU baselines (§7.2, and `/proc/schedstat` as in M2 §3.2);
  - the cooldown gate (§9.2);
  - the environment recorded before every run (§9.1).
- **Validity:** PROTOCOL §9.3, rules 1 to 4. Rule 3 applies: the point is unsaturated (§6.2 with A7). An invalid run is repeated once. An incomplete repetition is redone in the sweep's next session, as `docs/notes/comparison.md` says. The CV flag of §9.3 is reported.
- **The runs that count:** per repetition and variant, the valid run of the session that completed the repetition. An invalid ×2 run counts as missing.
- **The ambient temperature** is what the operator reports at each session's start. M1's session had 27 °C. The cooling is A9's.
- **Order checks:**
  - `tools/check_prereg_order.py` checks that every setup record starts after every record of the `m3_before` sessions.
  - It also checks that every `m3_after` session starts after the latest setup record before it had ended, and that this record passed on a fresh board. An earlier setup that passed does not count once a later one has run.
  - The session tool refuses `m3_before` on a board with a setup record, and `m3_after` unless the board's latest setup record passed on a fresh board.

## 4. Code, versions and records

- **Code:** `bench_main` and the tools at the commit A15 fixes, built on the board in both sweeps.
  - M1's binary was built at `86587a2`. Since then, the shared core and `bench_main` changed for M2 and M4: the option parsing, the header, the staggered sampler (off here), and the post-processing dispatch.
  - The default path's threads, affinities and queues were checked against M1's for M2 and for M4 (M4 §8 step 3). M3 does not check them again.
- **Pinned:** the session tool compares the board's inventory (`tools/inventory.sh`) with `docs/notes/inventory_m1.txt` (A10). It does not start if any of these keys differs:
  - the kernel, the boot firmware, and the NPU and RGA drivers, which come with the image;
  - ffmpeg-rockchip's version line, its configuration and `h264_rkmpp`'s defaults;
  - librknnrt and librga, by version and by SHA-256, with MPP's library;
  - the RKNN headers;
  - the build's type, flags, include paths and defines;
  - the model.

  The full list is A15's.
- **Not pinned:** every other line, mainly the Ubuntu packages' versions and the libraries' SHA-256. Each session writes its diff from `inventory_m1.txt` and its package list (`dpkg.tsv`), and §6 reports them.
- **Run kind:** `m3`, under `results/m3/`, for both sweeps and the setup record. Runs and records carry freeze-m3's commit in their headers (`freeze_m3_commit`).
- **What `bench_main` accepts:** a run of kind `m3` must be B or C at the main condition, with every option of §1 at its default.
- **Development records:** every run of M3's tools before `freeze-m3` is of kind `check`. A setup writes a `check` record unless four things hold: the board is fresh, it runs with its services, `freeze-m3` has its row, and the checkout's code equals `freeze-m3`'s.

## 5. What could go wrong, and what then

- **The setup fails on the reset board:**
  - The record says in which step.
  - If the cause is in the scripts, they are fixed by an amendment. The board is reset again, and the setup is rerun from the start.
  - If the cause is outside them, such as a mirror or a download, the board is also reset and the setup rerun.
  - Every attempt is reported.
- **A pinned key differs after the setup:** the session does not start.
  - If an amendment can restore the key, by a script change, the board is reset and set up again.
  - Otherwise, M3's outcome is "not determined", with the key and its values.
- **A run is invalid:** PROTOCOL §9.3, as in §3. A variant left with no run that counts makes the outcome "not determined".
- **Defects:** a departure of the code or scripts from this text.
  - It is fixed by an amendment, and every session that used the defective code is rerun whole.
  - Superseded runs stay under `results/` and are reported.
  - The criterion, the point and the reference values of §1 and §2 are not changed.

## 6. Reporting

- **The criterion:** the four comparisons of §2 for `m3_after`, with their relative differences, and the outcome. With them, §2's note on B's p50.
- **Descriptively:**
  - `m3_before` against M1, with the same four relative differences;
  - `m3_after` against `m3_before`;
  - system CPU (`/proc/stat` and `/proc/schedstat`), p99 latency, MPP hold time, drops and the highest temperature;
  - the values of every run.
- **The setup:**
  - its steps and their times;
  - what the operator had to do by hand;
  - every failed attempt.
- **What changed:**
  - each session's inventory diff from `inventory_m1.txt`;
  - the packages whose version differs between the board before and after its reset.
- **Release:** `v0.3-m3`, with the report `docs/report/M3.md` and the tables of `tools/m3_report.py`.

## 7. What M3 does not tell

- **About another board:** it is the same board, reset, with the same cooling and stream PC (#70).
- **About newer versions:** librknnrt, librga, the kernel and the drivers are the ones M1 used, by design. Only Ubuntu's packages move.
- **About M1's other results:** only H1's point is reproduced. H2's and H3's points, the sweeps and M1.1's designs are not.
- **About H1's verdict:** M3 does not judge H1 again.

## 8. Stages and values

1. **Development, before registration** (run kind `check`):
   - the tools: run kind `m3` in `bench_main`, the sweeps `m3_before` and `m3_after` in `tools/stream_session.py`, `scripts/setup_board.sh`, `scripts/reproduce_m1.sh`, `tools/m3_report.py`, and M3's order checks;
   - the smoke tests and the chroot tests of the Disclosure, and the review of the tools before registration.
2. **Registration:** this file and A15 together. A15 fixes:
   - M3's code commit;
   - the inventory keys of §4;
   - the fresh-board markers of §3;
   - the SHA-256 of librknnrt, the model and the video manifest, which the setup checks;
   - the setup's package list and the ffmpeg-rockchip commit;
   - the development runs' results.

   `prereg-m3`, `amend-A15` and `freeze-m3` tag the commit that merges them.
3. **Runs, after `freeze-m3`:** `m3_before`, the reset, the setup, then `m3_after` (§3).

## 9. Amendments

- **Numbering:** M3's amendments go to AMENDMENTS.md, numbered on from A15 (A16, A17, …).
- **PROTOCOL §15 applies** with `freeze-m3` in place of `freeze-m1`:
  - After it, a change to any of the following invalidates every M3 run that used it: the shared core, the decoder, B's or C's path, the session tool's M3 parts, or the two scripts.
  - Affected sweeps are rerun whole.
  - A change to the setup script after a setup also needs a new reset and setup.
  - Superseded runs and records stay under `results/` and are reported.
- **Releases:** every amendment made after `freeze-m3` is published as its own Release `amend-A<n>`.
