# Pre-registration M2: post-processing

- **Registration:** this file is stage 1 of M2's two stages and gets the tag `prereg-m2`. Its reference time is the `created_at` of the GitHub Release `prereg-m2`. That time is recorded with the tag's commit SHA in the Registration table of `docs/notes/env.md`.
- **Normative text:** this English file. `M2.ko.md` is a translation; if they disagree, this file governs.
- **Changes:** this file is not edited after `prereg-m2`. Later changes, and the values that §7 fixes later, go to [AMENDMENTS.md](AMENDMENTS.md), numbered on from A12 (§8).
- **Base:** [PROTOCOL.md](PROTOCOL.md) v1 applies, with the amendments in force (A1 to A12), except where this file says otherwise. Terms are PROTOCOL's. Verdicts, and the handling of points with fewer than 3 valid runs, follow [HYPOTHESES.md](HYPOTHESES.md) ("Verdicts").

## Disclosure: what was seen before this registration

- **M1 and M1.1:** all of their results, including the arrival phases found after the fact ([M1.1](../docs/report/M1.1.md#arrival-phases-found-after-the-fact)).
- **The exploration** of [docs/notes/m2_exploration.md](../docs/notes/m2_exploration.md), made on the board:
  - the runtime's output-path options;
  - the hazard of a CPU-written uncached input;
  - the timing of the post-processing prototype. Its version 4 took 0.129 ms per call against M1's 0.361 ms, on 300 frames of video ①.
- **What was chosen after it:**
  - the technique (§1);
  - the thresholds of M2-H1 and M2-H2 (§2). They are about half of the prototype's projection, 5.7% and 11.1% of C's process CPU;
  - leaving the output-flush option out.
- **Not yet run:** no pipeline run with the new post-processing.

## 1. What is compared

Two arms. Both are PROTOCOL §5.2's C, run from the same binary in the same sessions:

- **C:** M1's C, with M1's post-processing (`core/yolov8_post.cpp`, unchanged).
- **Cp:** C with the post-processing of the prototype's version 4 (`decode_branch_neon2` of `tools/post_probe.cpp` with its table and prefetches), moved into a file of its own.
  - **Scan:** NEON compares the score sums of 16 cells at once, and keeps an 80-class running maximum for each cell.
  - **Box decoding:** the softmax terms come from a table, and the outputs are prefetched.
  - **The table:** it holds `exp(b − m)` for all 256 × 256 pairs of quantized bins, computed with M1's expression. It is built once per (zp, scale) of the box outputs, at initialization, before the warm-up. So its build time is not in the window. Its 768 KiB shows only in VmRSS. A box output with a scale that is not positive stops the binary at initialization, before any run.
  - **What it must give:** M1's detections, field for field (§4).

The arm is chosen once, at start-up, by an option of `bench_main` (§7). Only the post-processing function differs. Everything in PROTOCOL §5.3's list is the same for both arms:
- the thread layout, the queues and the drop policy;
- the slot count and the output binding;
- where the post-processing runs: inline in the NPU worker, after `rknn_run`;
- the instrumentation and the per-buffer cache policy;
- the `rknn_init` flags: none of `RKNN_FLAG_DISABLE_FLUSH_*` (PROTOCOL §8);
- A6's label on C's zero-copy evidence, which applies to both arms.

Not compared in M2: B and A, the output-flush option, and post-processing on a thread of its own.

## 2. Hypotheses

Every result is stated with the conditions of HYPOTHESES.md: the pipeline is on cpu4–7, and the decoder's buffers are CPU-cached (A1).

### M2-H1: CPU at 8 channels, main condition

> At the main condition with 8 channels, Cp's pipeline process CPU usage (sum over cores) is at least 3% lower than C's.

- **Metric:** process CPU-seconds over the 120 s window (PROTOCOL §7.1), mean of 3 runs.
- **Spec-literal verdict:** with `C` and `Cp` the 3-run means, *adopted* if `(C − Cp) / C ≥ 0.03`, otherwise *rejected*.
- **Practical verdict:** the same threshold. The verdict is *indeterminate* in either of these cases:
  - in any valid run of either arm, some channel's inference rate is below 4.75 fps (PROTOCOL §7.4);
  - Cp's 3-run mean drop rate (PROTOCOL §7.5) is more than 1 percentage point above C's.
- **Secondary metric:** system CPU (§3.2). If `C − Cp` has the opposite sign on it, the result is also labelled *mixed*.

### M2-H2: CPU at 5 channels, auxiliary condition

> At the auxiliary condition (30 fps per channel) with 5 channels, Cp's pipeline process CPU usage (sum over cores) is at least 5% lower than C's.

- **Metric:** as in M2-H1.
- **Spec-literal verdict:** *adopted* if `(C − Cp) / C ≥ 0.05`, otherwise *rejected*.
- **Practical verdict:** the same threshold. The verdict is *indeterminate* in either of these cases:
  - in any valid run of either arm, some channel's inference rate is below 28.5 fps;
  - Cp's 3-run mean drop rate is more than 1 percentage point above C's.
- **Secondary metric:** as in M2-H1.

**Why the drop-rate condition:** a dropped frame costs no inference and no post-processing. The condition stops Cp from passing by doing less work. It is one-sided for the same reason as in M1's H2.

### What the decision rule can and cannot tell

- **No test enters the verdict.** It compares the point estimate of `(C − Cp) / C` with the threshold, as M1's H1 did.
- **Expected error rates, approximate:** these use M1.1's sd of C over 3 runs (0.26 s of 19.49 s at 8 channels, main; 1.41 s of 37.45 s at 5 channels × 30 fps). They assume independent runs, the same sd for Cp, and normal errors; they ignore the pairing below, and M1.1's sd comes from runs within one session. The standard error of `(C − Cp) / C` is then about 1.1% at main and 3.1% at auxiliary.

  | | Adopted if the true saving is 0 | Adopted if it is the projection |
  |---|---|---|
  | M2-H1 (threshold 3%) | about 0.3% | about 99% (projection 5.7%) |
  | M2-H2 (threshold 5%) | about 5% | about 98% (projection 11.1%) |

  At a true saving equal to the threshold, either verdict is about as likely as the other.
- **Pairing:** each repetition's two runs share a session (PROTOCOL §9.1). A shift of C between sessions therefore falls on both arms. From M1 to M1.1, C's process CPU rose by about 5% at both points (18.56 to 19.49 s, 35.68 to 37.45 s), across a change of session and of binary (A12).
- **Reported with each verdict:**
  - the three paired differences `(C_r − Cp_r) / C_r`, `r` = 1, 2, 3;
  - a descriptive 95% t-interval of their mean.
- **Flag:** an arm whose coefficient of variation of process CPU at the point is above half the threshold (1.5% at main, 2.5% at auxiliary). The flag changes no verdict.

A rejected hypothesis is a valid result. Before the runs, the size of the saving is known only from the prototype, which ran without the rest of the pipeline.

## 3. Changes for both arms

### 3.1 Staggered sampling at the main condition

- **In M1:** every channel sampled the frames whose decode-order counter satisfied `counter % 6 == 0`. M1.1 found that the sampled frames of the channels arrived close together: within 7 to 23 ms of each 200 ms in M1's 8-channel runs of B and C. Their spread changed from run to run, uncontrolled.
- **In M2:** the channel with index `k` in `bench_main` (`k` = 0, 1, …; channel `ch<k+1>` of [assignment_m1.txt](../stream-server/assignment_m1.txt), and `channel` = `k + 1` in `frames.csv`) samples the frames with `counter % 6 == k mod 6`.
  - **What this controls:** which frames a channel samples. Each channel's counter starts at 0 at its own first decoded frame (`core/pipeline.cpp`). So a channel's phase is its start offset plus `(k mod 6) × 33.3` ms. The rule sets the second term; the start offsets stay uncontrolled.
  - In M1 the start offsets were close: at 8 channels the phases lay within 7 to 23 ms. With such offsets, the sampled frames spread over the 200 ms. At 8 channels, channels 0 and 6 share a slot, as do 1 and 7.
- **The auxiliary condition is unchanged:** every frame is sampled, and the sampler cannot change its phases.
- **Measured for every run, at both conditions:**
  - the spread and drift of the arrival phases, as `tools/m1_phases.py` defines them;
  - at the main condition, the **stagger error**. With `φ_k` channel `k`'s phase, it is the largest circular distance, over `k`, between `φ_k − φ_0` and `(k mod 6) × 33.3` ms, on the 200 ms circle.
- **No run is excluded, repeated or adjusted for its phases or its stagger error.** They are reported next to the latency, which may depend on them (M1.1).

### 3.2 Metrics

- **Process CPU:** as PROTOCOL §7.1.
  - The per-cluster split of §7.1 is reported for both arms: the pipeline threads (cpu4–7) as A76, the metrics thread (cpu0) as A55, any other affinity as unattributed.
  - The split uses `bench_main`'s own attribution, which knows M1's affinity strings. M2 keeps those affinities.
- **System CPU (the secondary metric of M2-H1 and M2-H2):** for each CPU, the Δ over the window of the 7th number after the label of its `cpu<N>` line in `/proc/schedstat` (`rq_cpu_time`, in ns), summed over the CPUs, minus an idle baseline. The baseline is the same sum over 120 s with no pipeline running, measured once per session. The schedstat version is recorded; the field needs `CONFIG_SCHED_INFO`.
  - **What it counts:** the run time of every task other than the idle task, on every CPU: all processes, kernel threads and threaded interrupt handlers, with the interrupt time that falls inside them.
  - **What it misses:** interrupts handled while a CPU is idle. Time is added at each context switch, so a slice that spans the start or the end of the window is counted in the window it ends in.
  - **Why not `/proc/stat`:** M1.1 found its per-core counts much noisier than process CPU between runs of one arm, and some runs counted less than process CPU ([M1.1](../docs/report/M1.1.md)). Whether `/proc/schedstat` is steadier is not known yet; its between-run variation is reported.
  - `/proc/stat`'s system CPU (PROTOCOL §7.2) is still recorded and reported.
- **Reported, no verdict:**
  - latency p50 and p99, drop rate and inference rate (PROTOCOL §7.3 to §7.5);
  - the stage times, the post-processing among them (`t3` to `t4`);
  - the arrival phases and the stagger error (§3.1).

## 4. Equivalence of Cp (before `freeze-m2`)

- **Procedure:** a check tool runs both post-processings on the same NPU outputs.
  - **Frames:** every frame of videos ① to ④, 3,600 in all, read as `file_source` and prepared by C's RGA path. The outputs come from NPU core 0, as in M1-4.
  - **Synthetic outputs:** 12,500 sets of outputs with random box bins. Each set has 80 candidate cells, each of a different class, so NMS removes none of them. They are split 27, 27 and 26 across the three branches, so every table is used. That makes 1,000,000 box decodings in all.
  - **Code:** the tool links the same compiled post-processing objects as `bench_main`, from the build that the comparison runs use. It calls M1's `yolov8_post` as C runs it, not a copy of its parts.
- **Criteria:** on every frame and every synthetic set, Cp's detections equal C's: the same count, in the same order, with the same class, score and four coordinates as floats.
- **Why synthetic outputs too:** equality was shown for the prototype as built and tested, not by construction alone. GCC under `gnu++17` may contract a multiply-add differently in different functions ([exploration](../docs/notes/m2_exploration.md)). The video frames give few candidates per frame; the synthetic sets test many more decodings.
- **On failure:**
  - Cp is not run, and the cause is recorded in AMENDMENTS. The check is repeated in full after a fix, and the report states the failure.
  - A fix may change only how version 4 is written or built. For example, it may change where an expression is evaluated or the flags of Cp's file. It may not change the scan, the table or the prefetches. Any other change needs a new registration.
  - If no build passes, both hypotheses are reported as *not tested*.
- **The same objects in the runs:** the SHA-256 of the compiled objects of `core/yolov8_post.cpp` and of Cp's file, as built into `libcore` and linked into both the check tool and `bench_main`, is recorded for the check and for every session's build. `CODE_COMMIT` and the latest amendment are compiled into `bench_main.cpp` only, so an amendment does not change these objects. If a session's objects differ from the check's, §4's check is repeated with that build before its runs.
- **During the comparison runs,** reported with no verdict: each channel starts from the beginning of its video in every run, with continuous timestamps (PROTOCOL §3). So in each repetition, a frame of a channel is named by its `pts` modulo the video's length. For the frames that both runs of a repetition processed, the detection counts of `frames.csv` are compared: the number of frames compared and of differences are reported. A difference can also come from elsewhere in the pipeline, so it is investigated and reported, and it changes no verdict.
- **Not checked by this:** the M1 equivalence of C against B (PROTOCOL §11). Cp's detections are C's.

## 5. Runs

### 5.1 Run kind and header

- **Run kind:** `m2`, written under `results/m2/`.
- **Header:** PROTOCOL §1.4's fields, plus the commits of `prereg-m2` and `freeze-m2` (`none` before it), the arm's post-processing (`m1` or `neon`), and whether the sampler is staggered.
- **Order check:** `tools/check_prereg_order.py` also checks two things. Every `m2` run starts after `freeze-m2`. Every `check` run whose header names `prereg-m2` starts after `prereg-m2`.

### 5.2 Matrix

1. **Main:** C and Cp at 8 channels, × 3 repetitions, with 5 fps inference per channel and the staggered sampler (§3.1).
2. **Auxiliary:** C and Cp at 5 channels, × 3 repetitions, with 30 fps inference per channel.

Both points are unsaturated (A9), so rule 3 of PROTOCOL §9.3 applies.

### 5.3 Order and validity

- **Sessions:** as PROTOCOL §9: the cooldown gate, the idle baseline and the ambient temperature per session. The cooling is A9's.
- **Blocks:** two blocks of 6 runs, main first and auxiliary second. Inside a block, the arm order per repetition is C→Cp, Cp→C, C→Cp.
- **Repetitions:** the two runs of one repetition are never split across sessions (PROTOCOL §9.1).
- **Validity:** PROTOCOL §9.3, with its handling of invalid runs. Its flag for a CV above 10% is replaced by §2's.
- **Thermal check:** none is run for M2. M1-3's thermal check ran B at loads above M2's points; B at 5 channels × 30 fps used 131 s of process CPU per window, against about 37 s for C. Rule 1 of §9.3 still catches any clock below its fixed value.

## 6. Reporting

- **Verdicts:** both verdicts of each hypothesis, with `(C − Cp) / C` on process CPU and on system CPU, and the items of §2.
- **Also reported:**
  - the per-cluster split;
  - `/proc/stat`'s system CPU;
  - the latency, drop rate, stage times, arrival phases and stagger error of every run;
  - the CPU values of the check runs of §7, marked as checks;
  - M2's C against M1's C. This is exploratory: the main condition's sampler differs, and the sessions are not the same.
- **Release:** `v0.2-m2`, with the report `docs/report/M2.md`.

## 7. Stages and values fixed later

1. **`prereg-m2`:** this file.
2. **Implementation:**
   - Cp's post-processing, in its own file. `bench_main` gets an option for it, recorded in each run's `env.json`; the default is M1's post-processing.
   - The staggered sampler, as an option too, off by default.
   - The `/proc/schedstat` metric, run kind `m2`, the header fields and the order check of §5.1.
   - `core/yolov8_post.cpp` is not changed.
   - These change the shared core after `freeze-m1`. M1's and M1.1's runs are not affected, on two grounds, as for A12. They were made with their own binaries. And the default path, with both options off, runs as before: a run of C with the defaults is kept as evidence, as A12 kept `default_b` (step 3).
   - **What the default path does differently:** the CPU snapshot taken at the window's start and end also reads `/proc/schedstat`; the header and `env.json` gain M2's fields (§5.1). Nothing else changes in it.
3. **Checks before `freeze-m2`,** run kind `check`, each run starting after `prereg-m2` and naming it in its header. The equivalence check runs first; a fix under §4's failure rules repeats every check of this step.
   - the equivalence of §4;
   - a run of C with the defaults, at 2 channels, main condition (step 2). Its threads, affinities and `queues` in `env.json` must match those of M1's run `32_main_C_2ch_r1` (session `20261103T073439Z_main`);
   - one run of each arm at 8 channels, main condition, staggered. Its `frames.csv` must show that every sampled frame of channel `k` has `counter % 6 == k mod 6`. Its arrival phases and stagger error are recorded; they set no pass or fail.
   - in each of these two runs, `/proc/schedstat`: the raw window sum, over all CPUs, is at least the run's process CPU, and the Δ is above 0 on every CPU. If either fails, M2 has no secondary metric and no *mixed* label, and an amendment says so before `freeze-m2`.
   - The CPU values of these runs are reported. Nothing that §7 fixes may change because of them, except through the failure rules above.
4. **`freeze-m2`:** it tags the commit whose AMENDMENTS holds the values below. Its Release `created_at` is the reference time for M2's runs.

## 8. Amendments

- **Numbering:** M2's amendments go to AMENDMENTS.md, numbered on from A12 (A13, A14, …).
- **PROTOCOL §15 applies** with `freeze-m2` in place of `freeze-m1`, and with C and Cp in place of B and C:
  - before `freeze-m2`, measurements affected by a change are redone from scratch;
  - after it, a change to the shared core, the decoder, C's path or either post-processing invalidates every M2 run that used it, for both arms. Affected points are rerun as complete blocks.
- **Releases:** every amendment made after `prereg-m2` is published as its own Release `amend-A<n>`.
